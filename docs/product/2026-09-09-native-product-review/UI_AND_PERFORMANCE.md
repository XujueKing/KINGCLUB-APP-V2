# UI 保真、原生体验与流畅度验收

- 状态：**In Review**；本文件定义验收方法与建议预算，不是已完成的截图审计或性能报告。
- 已确认用户目标：对旧版 UI 保持 99% 类似；可以边实现有效业务流程边微调 UI，不要求复制旧内部代码与容器限制。

**2026-09-10 新参考与范围**：聊天按微信熟悉体验尽量 1:1；中央内容/创作和“我的”参考抖音；储物箱采用游戏式物品表达；管理能力按 App 角色隔离。首版不做实名核身，旧 KC-P-005 任务/文案须按照片上传方法重审。这些是用户明确方向，具体线框/交互尚待验收；详见[需求台账](REQUIREMENT_INBOX.md)。

## 1. 什么保持，什么允许改

保持 KING CLUB 品牌颜色、字体层级、图标/素材、主要间距与布局、卡片/弹层、核心入口、文案语义及用户熟悉的流程。微信/抖音作为明确模块的交互与布局参考，不混用第三方品牌资产冒充其产品；五目的地不变，用户新增创作/游戏/管理部分先补设计，不能对没有旧版参考的新页宣称“99% 已还原”。

允许且需要适配系统安全区、刘海、手势返回、键盘、字体缩放、系统权限框、无障碍、图片解码与媒体播放。旧平台导致的误触、卡死、假成功、过期状态和安全缺陷不能当成保真目标。

## 2. 99% 如何测，而不是口头宣布

当前建议将 99% 定义为**受控视觉基线下的逐页目标**，不是“所有屏幕像素必然 99% 相等”，也不是项目完成率：

1. 确认原型提交、设备、尺寸、系统/字体、数据与页面状态，获取脱敏的旧版截图/录屏及 V2 对照。
2. 每页登记所有入口、正常/加载/空/错误/离线/权限等适用状态；首页内部 Tab、聊天面板、发布多步骤不能只计一个路由。
3. 对可直接比较的稳定应用内容区域，建议视觉 diff 目标 ≤1% 差异像素；差异阈值先用代表页校准，再由用户确认，不因测试失败临时放宽。
4. 遮罩仅用于明确登记的时间、电量、动态媒体/数据和平台系统区域。字号、布局、控件、按钮、错误信息不能遮掉以制造达标。
5. 字体抗锯齿等跨平台差异可以人工标注豁免；大块位移、颜色/图标错误、缺少入口不能用平均分掩盖。每页都有人工结论和差异说明。
6. 交互与业务路径单独验收：关键任务入口、返回、按钮动作、同一对象状态对应必须全部符合批准要求；不能因截图像而让按钮无功能。

用户检阅可以要求纠正具体页面；任何较大的视觉差异都先列变更理由再确认。当前没有逐页新截图证据，**不能声称已达到 99%**。

## 3. 测试矩阵

| 维度 | 必测范围 |
|---|---|
| 设备 | Android 中低端/主流机型与 iPhone，至少覆盖最小支持系统和较新系统；具体型号待提供 |
| 布局 | 窄屏、主流 393×852 逻辑尺寸及大屏；安全区、底部手势、长文案 |
| 文字 | 默认、放大字体，重点复验 200%；不得裁掉金额、提交与返回按钮 |
| 交互 | Android 系统返回、iOS 手势返回、键盘弹出/收起、扫码取消、媒体进入/退出 |
| 生命周期 | 前后台、旋转策略、系统回收后恢复、账号切换、顶号/注销 |
| 网络 | 正常、慢网、高延迟/丢包、离线、请求超时与恢复；图片/视频失败可单独重试 |
| 可访问性 | 控件语义标签、阅读顺序、可点击区域、对比与非颜色状态提示；用平台工具和真机验证 |

截图/录屏/性能附件保存在项目外归档，文档登记路径、哈希、版本和时间；遵守仓库内容策略，不把生产用户资料或大型附件推送 Git。Golden 基准图只保留测试必需版本。

## 4. 性能预算（当前建议，需基准测量后冻结）

使用固定账号规模与合成业务数据、固定网络场景、明确设备和构建模式，多次采样报告 p50/p95；不得用 Debug APK 在模拟器上的感觉作生产结论。Flutter 官方建议在 profile 模式与目标设备分析性能：[性能分析](https://docs.flutter.dev/perf/ui-performance)。

| 项目 | 建议目标与口径 |
|---|---|
| 普通列表/动画 | 60Hz 设备以约 16.7ms 帧预算测试，滑动测试掉帧占比 <1%；高刷新率按实际帧周期复核，不把 60fps 冒充 120fps |
| 首次启动 | 约定中端机 release 冷启动，首帧 p95 ≤1.5s，首个可交互本地界面 ≤2.5s；网络鉴权等待分开计时 |
| 常用页进入 | 有缓存时 100ms 内给出本地可见反馈；后台刷新不阻塞已展示内容，无缓存有明确骨架/进度 |
| API 只读 | 测试环境端到端 p95 ≤300ms，分页有上限；外部依赖时间单列 |
| 业务写入 | 不含第三方支付/短信/转码的短事务 p95 ≤500ms；超时是待确认而非自动失败 |
| 聊天 | 输入/发送立即本地可见，正常网络持久化确认 p95 ≤500ms；在线端到端送达暂定 ≤1s，离线补偿单独测 |
| 视频 | 已缓存首画面建议 p95 ≤500ms；标准网络首次播放 ≤1.5s；记录首帧、卡顿时长、错误率与切换次数，不保证弱网零等待 |
| 稳定性 | 灰度期建议 crash-free sessions ≥99.9%；统计窗口、样本量与 ANR 单列，低样本不能宣称达标 |
| 正确性硬门槛 | 重复扣款/记账、越权、跨账号缓存泄露、持续对账差异为 0 个未解决问题；不能用性能换正确性 |

这些数字是提案，不是当前实测 SLA。并发用户、消息速率、商品/订单量、视频规格与网络成本未知，容量目标应在生产基线采集后由用户确认；不提前承诺百万并发。

## 5. 实现方向

- 页面局部订阅状态，减少整页重建；大列表按页/游标加载，有限图片缓存与解码尺寸。
- 不在 UI 线程做大 JSON 处理、压缩和全量排序；视频最多保留批准数量的活动实例，暂停不可见页。
- 媒体优先缓存与适配码率，弱网限制预加载；进度绑定作品 ID 和源版本，不能错误恢复别的视频。
- API 限量分页、覆盖索引、关键查询 explain/压测；不无限增大 MySQL 连接池或给所有查询加 Redis。
- 转码/合成独立 worker，队列隔离与背压，避免媒体任务拖垮登录和交易。
- 可观测性区分 UI、网络、数据库、第三方和队列耗时，以 requestId/traceId 定位，禁止采集真实消息或完整支付请求。

## 6. 当前 V2 的验收前置整改

现有审计 A02/A03 的会话守卫与封面隔离优先；接着是资料/准入草稿、好友/聊天同对象状态、VIP 创建/支付/管理、AA 零现金/分桌和整数分贯通；最后稳定 Golden 并做双端整流程验收。

当前已知 2 项偏好 Golden 失败及聊天 Golden 偶发差异须归因；不覆盖基准或加豁免来冒充修复。此前构建和单页通过不替代本轮新增范围的 UI 验收。

## 7. 新增体验专项（待规格冻结）

- 聊天：先选定微信参考版本/目标机型，逐项对照输入框、键盘/语音/表情/加号切换、消息长按、引用/转发、发送失败、媒体预览、返回。礼物/付款/AA/游戏/推荐是 KING CLUB 扩展，单独验收，不假称微信同款原生功能。
- 中央内容：推荐/关注与好友范围、拍摄入口和游戏大厅层级清晰；切换保持位置，后台停止不该播放的声音。中央本来已有内容 Tab，历史“中央扫码”描述不作为当前基线。
- 私人储物箱：酒、团购券、赠券、道具可区分且可读，数量/有效期/使用状态不被装饰盖住；游戏式表达不自动增加随机开箱/抽奖。
- 我的与管理：照片/作品、余额/账单、设置与个人任务易达；管理入口只对授权角色可见，切换身份/失权后清理管理页和缓存。
- 首版照片准入：无实名核身 SDK 页面和强制活体步骤；上传/检测/待审/补件/重试可演示，不能用“实名认证成功”文案描述照片审核成功。
- 媒体：按[压缩/美颜调研](MEDIA_AND_FACE_RESEARCH.md)补质量、体积、耗时、掉帧、温升、色彩/音画同步、取消/重试与权限矩阵；所有指标在真机测量前保持建议值。
