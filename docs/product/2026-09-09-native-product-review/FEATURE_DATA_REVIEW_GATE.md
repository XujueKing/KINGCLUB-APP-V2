# 每功能数据库与数据链路审查门禁

- 状态：**Mandatory / 每个功能实施前强制执行**。
- 用户确认：2026-09-10，所有功能涉及的数据库表都要逐功能审查。
- 业务基线：用户确认旧数据库和逻辑没有问题；审查目的是完整继承业务并改进表达、约束和工程架构，不是预设旧实现错误。
- 范围：旧小程序、旧 Java、`s_interface` 分类、`K_` Routine、KING CLUB `k_` 表、必要公共依赖、CCSOP 新模型与迁移验证。

## 1. 为什么必须逐功能过表

旧系统的真实业务并不只存在于页面或一张主表中。一个旧接口可能通过 Routine、触发器或 Java 直连同时修改会员、钱包、奖励、消息和审核图片；只根据表名迁移，会漏掉副作用、重复资产或把历史耦合继续带入新架构。

审查必须同时记录旧实现已有的正确保障。已核对的注册 Routine 使用事务、异常处理和回滚，不能为了说明重构价值而把旧系统误写成会产生半套资产。重构的验收底线是**业务语义和一致性不退化**。

统一现代化边界见[数据库现代化原则](DATA_MODERNIZATION_PRINCIPLES.md)：继续使用 MySQL 8.4，不为追新强制移除存储过程，不把微服务、ORM 或拆表本身当成质量证明。

每个功能应以“用户动作 → 接口 → 事务/Routine → 直接表 → 间接副作用 → 外部服务 → 新模型 → 对账”形成闭环。旧代码用于发现业务事实，不作为新实现必须复制的结构。

## 2. 强制检查维度

每个 `docs/features/**/feature_*/` 在接真实接口或创建 migration 前必须有 `database_review.md`，至少完成：

1. **功能边界**：入口、角色、正常/失败/补偿路径和不属于本功能的副作用。
2. **旧接口目录**：用 `s_interface.interfaceType → s_interface_type.typeId/parentId` 确认酒吧分类，同时核对客户端静态调用、Java 专用 HTTP、回调和定时任务。
3. **旧数据对象**：列出直接读写的 `k_` 表、递归 Routine 依赖、触发器/事件及必要非 `k_` 公共依赖；非 `k_` 不自动取得迁移授权。
4. **字段语义**：主键/业务键、状态枚举、金额/时间/时区、软删除、空值、敏感等级、归属与历史脏数据。
5. **一致性边界**：事务、锁、幂等、并发、迟到响应、重试、部分成功和补偿；禁止用客户端自报状态放行。
6. **CCSOP 去向**：逐表/逐字段标记复用、拆分、合并、重建、只读归档或不迁移；新表、Routine、接口必须按 CCSOP 目录治理登记。
7. **迁移与验证**：基线时间点、转换规则、拒绝/隔离数据、数量/引用/资产对账、双读或影子验证、回滚与切换条件。
8. **安全与合规**：最小权限、加密/指纹化、日志脱敏、保留与删除、审计事件、导出和运营访问边界。

## 3. 状态和退出条件

| 状态 | 含义 | 允许动作 |
|---|---|---|
| `Not Started` | 尚未逐功能核对 | 只允许需求整理 |
| `Inventory Complete` | 旧接口、表和副作用已列全，但新模型未批准 | UI/Mock、合成数据测试 |
| `Model In Review` | 字段映射、事务和迁移方案已形成 | 契约评审；不得执行生产迁移 |
| `Approved for Isolated Integration` | 数据审查、接口契约和安全前置已批准 | 隔离环境 migration/adapter/联调 |
| `Rehearsal Verified` | 合成及脱敏快照迁移、对账、回滚演练通过 | 预发布评审 |
| `Production Approved` | 另行取得生产切换批准 | 按批准 Runbook 执行 |

功能不能因“页面可用”“单个接口返回成功”或“找到主表”跳过数据审查。存在未解释的接口、字段、状态或资产差异时，状态不得高于 `Model In Review`。

## 4. 每功能文档模板

```md
# <功能名>数据库审查

- Feature ID / owner / 状态 / 来源版本
- 用户动作与事务边界
- 旧入口及 s_interface 分类证据
- 旧表/Routine/触发器/Java/第三方依赖矩阵
- 关键字段、枚举、敏感等级与已知数据异常
- CCSOP 目标对象与逐字段去向
- 明确不迁移及拆出的副作用
- 幂等、并发、补偿和审计
- ETL、对账、回滚、切换
- 未决项、验证命令与证据
```
