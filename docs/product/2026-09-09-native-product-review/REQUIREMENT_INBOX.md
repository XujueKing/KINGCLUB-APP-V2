## 1. 持续整理规则

1. 每批按日期记录，每条分配稳定 RQ 编号；不改旧编号、不静默覆盖用户原意。重复需求合并引用，有变化追加变更记录。

3. 需求进入 PR 主表，关联工作包和验收。旧的暂缓/不做项遇到新明确需求，以新指令为准并标注历史差异。

5. 以后每次补充同步说明：新增了什么、修改了什么、哪些需要后续确认。尚未给出的需求不凭“等等”无限扩张。

### 同日追加决定：RQ-20260910-22

- 用户原话：“实名核身第一版不做，还是用旧的方法，照片上传的接口”。
- **已确认范围**：首版不接实名核身 SDK、活体核身或权威库比对；不以腾讯开通、采购或核身通过作为首发前置条件。只保留未来候选，不自动排到下一个版本。
- **首版方式**：以旧 `utils/registration-photo.js` 和 Java `/kingclub/registrationPhotoUpload?imageType=...` 对应的照片上传、检测/评分、会员审核业务链为原型。已核对旧上传使用 multipart 并返回暂存令牌，再由业务读取照片；它不是实名核身接口。
- 旧 `imageScoreApi` / `detectFaceApi` / `isUnderageApi` 分别承担的后续检测与现网对应版本需在 R1 对齐；不因为名称含“认证”就把它们归为权威 KYC。
- 迁移到 CCSOP 的既定方向不变：沿用照片接口方法及业务语义，补齐安全身份、令牌归属/用途/有效期、格式/大小/解码限制；新接口是否保留兼容路径在契约里明确，不让 Flutter 直接复制旧共享鉴权。
- `photoSubmitted`、`photoReviewStatus`、`appearanceAssessment`、`membershipStatus` 与 `kycStatus` 分开。没有可信实名证据时不得写 `verified`；也不批量清除历史已有可信核验记录。
- 原有实名页 KC-P-005 的页面任务、标题和前置条件进入变更评审，不直接删除路由或把 Fake 成功当生产实名。既有成年限制等业务规则单独核对，本指令不自动取消这些规则。
- 颜值检测与自研美颜仍保留。首版沿用旧照片方案，不在自建模型验收前停用/替换既有评分；不把“自研研究”默认为“首发必须换模型”。
- 关联：PR-03、PR-34；W10；D01、D05、D08。本台账当前累计 **22 条**。

## 3. 本批确定的产品结构

五个既有一级目的地为：首页、消息、中央内容、私人储物箱、我的。用户本批说明与 2026-08-26 已批准 Shell 的五目的地一致，扩展的是内容创作/美颜/游戏大厅、储物权益和管理能力；少数历史索引仍写“中央扫码”，需纠正，**不是现在新改成扫码 Tab**。

- 首页：广告、一起玩、受控扩展入口。
- 消息：微信式聊天体验 + KING CLUB 业务扩展。
- 中央内容：推荐/关注及好友内容、照片/视频创作、原生美颜、游戏大厅入口。
- 私人储物箱：存酒、团购券、赠券、游戏道具。
- 我的：抖音式个人主页、余额/账单、作品/照片、设置和相关个人服务。
- 登录/注册/照片审核：进入业务前的身份会话和会员流程，不是额外底部 Tab；实名核身首版不做。
- 扫码点单：保留独立快捷入口，具体位置随首页/聊天等入口评审，不抢占中央内容目的地。
- 管理员：纳入 App 产品能力，通过角色授权入口承载；具体在“我的”还是其他工作台位置待评审。普通会员不显示管理工具；是否补充大屏 Web 工作台另行决定，不能以此取消 App 管理能力。
