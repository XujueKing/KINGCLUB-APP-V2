# KING CLUB 数据和 API 迁移方案

- 状态：**In Review — 设计，不是可直接执行的迁移脚本**。
- 已确认用户边界：只将 `k_` / `K_` 表认定为 KING CLUB 业务表；混包中的其他网站不能整体迁入或修改。
- 已确认用户方向：旧过程不必照搬，可以重新建模和重构；必须保留正确的业务与资产语义。

**2026-09-10 最新范围澄清**：首版保留旧腾讯照片实名认证（姓名＋身份证号＋照片），不接新增 App 活体核身 SDK。旧后台实际为 ImageRecognition/DetectFaceAttributes，新 CCSOP 正式 adapter 待建；见[接口核查](../../features/identity/feature_member_onboarding/2026-09-10-tencent-adapter-review.md)。模块独立 UI 验收后允许隔离测试联调，不等于准许真实用户/生产数据迁移；混库 k_ 归属边界不变。

## 1. 如何确定范围

同时检查三条证据：

1. 数据归属：94 张快照 k_ 表 + 后续脚本的候选增量表，全部登记去向。
2. 业务目录：酒吧分类树内 103 个快照接口 + 3 个群管理增量，含前端、服务端、支付回调等用途。
3. 实际调用：72 路由、82 个静态编号、Java 专用 HTTP、Routine 调用及触发器/任务副作用。

三份完整结构清单见 [路由](inventory/LEGACY_ROUTES.md)、[接口](inventory/LEGACY_INTERFACES.md)、[表与字段](inventory/LEGACY_TABLES.md)。静态编号、表名前缀或分类任何一项都不能单独证明某个功能已完整迁移。

公共依赖只迁移必要语义：

| 依赖 | 旧用途线索 | 当前建议 |
|---|---|---|
| s_interface / s_interface_type | 调用登记、分类、旧 SQL 与参数格式 | 只取 KING CLUB 分类元数据作映射输入；新 interface、分类、Routine 目录重新登记，不导入所有网站接口或原样 interfaceSql |
| g_sms | 旧注册验证码 | 替换为新挑战/短信 Router，不搬历史短信凭据或验证码 |
| id_config / getGenerateId | 共享编号规则 | 使用新底座编号能力和显式旧 ID 映射，不复制其他项目的序列状态 |
| software_update | 版本信息候选依赖 | 独立发布/升级元数据，不导入其他产品发布记录 |
| Java 支付/文件/推送/搜索及共享身份 | 未必经过 s_interface；源码版本尚未对齐 | 核对专用入口/回调、共享表和外部资源；凭据、商户号与物业数据不直接复制 |

## 2. 先补齐时间与版本缺口

快照导出头和后续改进并不同步。必须取得一个明确时间点的 schema/数据/文件资源版本与增量边界，不能拿 6 月快照覆盖正在运行的 9 月业务。

已识别待补输入：

- 当前线上匹配小程序的 Java 构建/源码：用户目录与 online/clean 参考记录不一致。
- 群聊 `20260830_group_chat_complete.sql` 是否执行及执行后结构；其中新增成员关系与入群申请表。
- 注册照片 20260829、资料 20260831、颜值展示 20260901、媒体/音乐 20260905～06 的最终 SQL/服务修改及部署记录。
- 现库表数、记录范围、当前有效会员/资产/订单、binlog 配置/保留时间、日增量、备份恢复能力和第三方媒体对象可访问性。

这些输入不全时可以继续设计和合成数据测试，不能宣称迁移源已完整。

## 3. 旧字段到目标语义：第一批重点

下表是当前建议，不是最终 DDL。完整 1484 字段的转换表达式、空值/枚举策略、校验和拒绝规则需要逐域补齐并批准。

| 旧对象/字段 | 目标语义与处理 | 校验 / 禁止事项 |
|---|---|---|
| k_user.userAccount | legacyIdentityMap 对应既定 U... 账号与 KingClub 成员 | 不根据手机号相同就静默合并；冲突进人工处理；不新造 personId 体系 |
| k_user.userMobile | 身份权威手机号绑定的受控证明/映射 | 不能直接覆盖权威绑定；不能把本地缓存手机号当认证 |
| k_user.userStatus / isAuth / facialAuthenticationStatus | 分开账号状态、KYC 状态与会员资格 | 不把非零统一变为 approved/verified；保留来源和审核证据 |
| k_user.password / userSalt | 旧凭据不可直接视为新登录令牌 | 新短信登录与支付安全重新建立；不将旧哈希复制为新明文秘密 |
| userIDCard / userIDCardUrl / 审核照片 | 单独敏感材料域、受限访问与必要性/保留期评审 | 原始资料不放公共头像、测试 seed、日志或 CDN 公开路径 |
| k_user_info 扩展字段 | 按本产品目的确认保留/展示/受限归档 | 健康、政治属性、家庭资料等不因旧表有字段就默认继续采集或跨 App 共享 |
| k_user_relation | 区分邀请码、代理归属、经营关系 | 不直接转换为好友；独立权限和有效期 |
| k_conversations.memberIds / manageList | 精确 conversationMember / role 关系 | 去重、孤立账号、无主群、退出/删除、CSV 分隔异常；不使用 LIKE 匹配身份 |
| messages.messageId / parentId / messageStaus | 保留旧引用映射，新增稳定消息 ID、会话序号、明确状态 | 不按时间单独排序；引用目标缺失安全降级；保留删除/可见性语义 |
| k_order / k_order_member / k_stand_order | 分开场次/组局、参与预订、用户交易订单 | 一个旧 orderId 不必等于一张消费者付款单；逐种业务验证归属和父子关系 |
| decimal 金额字段 | CNY 整数分（或精确 DECIMAL 存储后受控转换） | 以十进制精确转换，拒绝超精度/越界，不使用 JavaScript 浮点乘 100 后随意四舍五入 |
| k_goldcoin_detail / diamond / exp | 各自资产数量及流水 | 不将金币数量当人民币分；兑付/折算规则版本化 |
| k_wallet / balance_details | 期初余额、冻结、历史分录、期末对账 | 不能只迁余额、漏冻结/未决；差异隔离，不自动补零或删流水 |
| transaction / notify / refund | 原交易、支付尝试、回调、退款及第三方单号映射 | 不重放旧回调以触发新扣款；导入状态不得自动调用支付供应商 |
| coupon / stored_wine / stored_items | 有效券、存酒/物品与剩余额度/数量 | 确认部分使用、失效、冻结、领取记录及关联员工；有效权益不得漏迁 |
| user_works / files / 图片与视频 URL | 作品与带所有权/用途的 MediaAsset、原对象映射 | 文件存在、摘要/尺寸/类型、私密权限、音乐使用证据独立检查；不能只复制 URL |
| datetime / scheduledTime | 明确原时区 + 营业日 + 绝对时间 | 跨零点营业日单独字段；零日期/非法日期进入拒绝报告，禁止猜测改正 |

## 5. 迁移实施顺序（当前建议）

### M-D0：范围、备份与隔离

先冻结 sourceRevision/时间点、k_ 允许清单、公共依赖例外、历史范围、业务规则及每域责任人。验证备份可恢复后准备完全隔离的 staging；导入账号无生产写权限、无短信/支付/推送凭据。

### M-D1：提取与新模型

不把整份 SQL 喂给新 CCSOP。优先由受控导出/ETL 提取批准的表和列，结构与业务数据分开。移除或不执行旧 DEFINER、GRANT、触发器、事件、外部调用和其他网站对象；原始快照仍只读保存。

旧库是 MySQL 5.7，新库目标 8.4。原地升级不能跳过支持路径；[MySQL 官方升级路径](https://dev.mysql.com/doc/refman/8.4/en/upgrade-paths.html)要求 5.7 经 8.0 再到 8.4。本方案建议**新库建模 + 受控数据转换**，不是直接升级旧实例，也不保证原 SQL 可原样导入 8.4。

对字符集/排序规则、大小写、保留字、JSON、零日期、严格模式、索引长度/唯一性变化和 SQL MODE 做专项测试。新对象一律递增 migration + 目录登记 + 文档 + 测试。

### M-D2：映射与可重复批量迁移

建议顺序：身份映射与成员 → 配置/商品/门店 → 关系/会话 → 历史内容/媒体 → 预约/订单 → 账务/权益 → 审计及运营数据。

每批记录 source、runId、checkpoint、输入/成功/拒绝/隔离数量与摘要；以旧业务 ID 唯一去重，可中断续跑；错误记录进入受控隔离区，不丢弃、不泄露原始值到普通日志。只迁移状态，不重新触发充值、奖励、支付、短信或公开发布副作用。

### M-D3：校验与差异处理

- 数量：批准范围内每表/分区输入数 = 成功 + 明确排除 + 隔离，逐项解释差异。
- 引用：账号、会话成员、引用消息、订单父子、支付/退款/凭证链完整；孤立数据有处置记录。
- 资产：逐账号/资产类型核对期初 + 收入 − 支出 = 期末，同时核对冻结、退款、未决和实际第三方交易；不能仅验总行数或总金额。
- 权益：券、存酒、门票、未结订单、待退款/待领取等有效权利优先保证完整。
- 媒体：对象存在、归属、可见性、合法用途与可访问性核验，缺失对象列入补偿单。
- 行为：旧/新用相同合成输入对照有效业务规则；已确认的旧漏洞不能作为新系统必须保留的输出。

迁移完成报告必须包含拒绝/差异/孤立记录统计、敏感数据处置和抽样追溯，不在报告粘贴真实个人行。

### M-D4：并行期增量与唯一写入方

小程序仍在使用，不能将旧源库全局改成只读。先定义**每个领域在每阶段只有一个权威写入方**：

| 阶段 | 业务写入 | 同步与读取 | 退出条件 |
|---|---|---|---|
| 历史迁移/影子比对 | 旧服务保持权威 | 快照+有水位的增量到新库；V2 影子只读核对 | 数据/权限/金额一致 |
| 单域灰度切换 | 指定域改由新服务权威 | 旧客户端经该域兼容层或路由适配也进入新写入方；其他域仍旧权威 | 双端同域结果一致且能回滚 |
| 观察与收缩 | 该域保持新权威 | 停旧写路径，保留受控历史查询/补偿窗口 | 观察期与账务/客服验收通过 |

增量方案需核实 binlog/CDC 能力；若不能提供无缺口增量，采用批准的短写停顿/最终补差方案。不要仅按 updatedDate 轮询却宣称不会漏删除或同时间更新。

禁止客户端或两个服务“尽力双写”同笔余额/库存。跨库复制、Outbox/CDC、兼容层的所有权与失败处理必须有演练。

### M-D5：切换、回滚与最终验收

先在隔离环境恢复演练，再按账号/门店/领域放量。回滚不是切开关就恢复：新写入开始后，必须处理新订单、退款、媒体与消息的反向兼容/补偿；不允许切回旧快照丢掉已产生的交易。

每次生产切换另行确认具体环境、允许表/接口、时间窗口、备份、写入水位、回滚执行人、客服通知与验收结果；本轮不执行。

## 6. 数据不做清单

不复制混包里的全部用户/物业/停车/政务业务，不读取或公开非必要真实个人字段，不导入旧生产凭据/验证码/设备令牌，不直接全库清空导入，不执行旧触发器来“自动修复数据”，不因为后台功能暂缓就删除其资产/历史。

本方案也不意味着永久保留所有敏感原始资料：迁移与归档必须按批准的目的、范围、权限及保留期执行，待用户/业务与合规负责人确认。

## 7. 09-10 新需求的映射补充（待详细契约）

- 照片上传：旧 `registrationPhotoUpload` multipart + imageType + 暂存令牌是首版业务原型；核对后续检测/评分接口的参数和令牌生命周期，再设计 CCSOP 操作/兼容入口。不得把一次成功上传当身份核验成功，历史照片不重新触发付费检测，除非另行批准。
- 评分迁移：`appearanceScore` 单列来源/算法版本和评估时间，未知版本明确标记 legacy-unknown；旧分数与自建分数不能直接等值互换。照片质量、颜值、会员资格、KYC 分开，未核身不写 verified，也不清除原有可信核验记录。
- 券：购券和赠券分别追溯订单或赠送来源，核对剩余次数/价值、适用门店/商品、有效期、核销/冻结与退款撤回；储物箱仅聚合展示。
- 道具：本轮新需求不证明旧库已有完整游戏道具表。先核对 k_ 库接口依赖；确需新对象通过新 migration 登记，不能把任意其他网站游戏表迁入或把历史金币自动变成道具。
- 管理：代理归属/会员授权、佣金规则和订单关联、桌台/商品库存、收银/交班、财务结算逐项映射；旧管理员标志不能直接授予全站/全门店权限。只把批准的角色/范围迁入新授权模型。
- 媒体派生：原对象、展示图、缩略图、转码视频等显式关联，保存处理策略版本和摘要；不覆盖原始来源对象，不以删原图获得“压缩完成”。
