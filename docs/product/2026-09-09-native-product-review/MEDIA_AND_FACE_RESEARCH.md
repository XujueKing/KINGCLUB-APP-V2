# 媒体压缩、人脸核身、颜值评估与原生美颜

- 调研日期：2026-09-10；需求来源：[第一批碎片需求](REQUIREMENT_INBOX.md)。
- 状态：**In Review**。官方能力事实与本项目选型建议分开；未开通服务、未接 SDK、未跑模型/媒体性能测试。
- 结论：腾讯企业人脸核身有接入路径；自研美颜和颜值评估可分别验证，但开源不等于完整产品、免费商用模型或零运营成本。

**用户同日追加决定优先：首版不做实名核身，沿用旧照片上传接口。**下文腾讯核身的技术/资质调研仅为未来参考，不是首发选型或接入任务。首版照片方案见第 0 节。

## 0. 首版已确认：旧照片上传方式

已核对：旧小程序 `utils/registration-photo.js` 调用 `/kingclub/registrationPhotoUpload?imageType=...`；提供的 Java 接口接收 multipart 文件和 imageType，调用 `stageRegistrationPhoto` 暂存并返回令牌，再供业务读取。原文件不因压缩/迁移被删除。

首版沿用这条上传方式和后续照片检测/评分、会员审核流程；具体参数、后续 `imageScoreApi` / `detectFaceApi` / `isUnderageApi` 关系以匹配线上版本的契约为准。CCSOP 承接新服务的总体方向不变，安全上下文与上传令牌治理不能沿袭旧漏洞；是否保留兼容 URL 在 R1 明确。

首版不接腾讯实名核身 SDK/权威库，不设置“核身通过才能注册”的门禁；照片上传/人脸检测/会员审核通过均不得自动写 KYC 已验证。旧审核与成年规则仍需逐项对齐，不把估龄当权威年龄证明。自建评分先验证，不能未达标就替换现有付费评分；自研美颜另行推进且不处理准入评分素材。

## 1. 必须分开的四种能力

| 能力 | 回答什么问题 | 对 KING CLUB 的意义 |
|---|---|---|
| 实名/活体人脸核身 | 是不是真人、是否对应声明的身份 | 注册/身份风控；权威库验证与自传照片比对必须区分 |
| 照片质量检测 | 是否清楚、曝光/角度/遮挡是否适合当前用途 | 上传前提醒重拍，减少无效处理；不是颜值分 |
| 颜值评估 | 在某套样本标注标准下的主观外观评分 | 用户明确的重要流程；用途和规则需单独确认，不能用来证明身份、真实年龄或健康 |
| 美颜 | 如何让用户选择的照片/视频呈现不同效果 | 原生拍摄/创作能力；不会提升实名证据可信度，不得处理核身输入 |

已核对提供的旧 Java：`KingClubApi.java` 的 `/detectFaceApi` 调用 `KingClubService`；后者调用腾讯 `IaiClient.DetectFaceAttributes` 并读取 Beauty、Age、Gender。这里只记录调用/字段，不复制密钥、原图或日志。该目录仍有[版本匹配缺口](SOURCE_BASELINE.md)，不能等同当前线上计费版本。

## 3. 自己做颜值评估，能否不付腾讯调用费

**技术上可以研究自建推理服务；本轮不能保证已有可直接商用、等同腾讯效果的免费模型。**节省的是第三方逐次 API 费用，仍有合规数据、标注、训练/推理、服务器、测试与运维成本。颜值没有统一客观真值；不能随意套一个“黄金比例公式”就称高准确率。

腾讯 `DetectFaceAttributes` 支持选择 Beauty 等属性；照片质量与外观属性是不同输出。自建替换需对照真实旧用途，不应继续采集一整组无业务必要的属性。[官方 API](https://cloud.tencent.com/document/api/867/71629)

一项明确的开源风险：常见 SCUT-FBP5500 颜值数据集的作者仓库写明仅用于非商业研究。不能因为可以下载，就用其数据/相关模型直接训练和上线商业 App；需逐项取得适用授权。[作者发布仓库](https://github.com/HCIILAB/SCUT-FBP5500-Database-Release)

建议验证路径（未实施）：

- A：先核实旧评分用途、当前调用量/成本和阈值。按授权照片做拍摄质量检查，减少无效付费调用；缓存必须绑定账号、用途、照片摘要与算法版本。
- B：只使用具有对应商用及训练授权的数据/模型；若没有合适现成授权，以另行同意的样本和人工多评审标注进行小规模验证，不抓取好友/社交照片或挪用核身原件。
- C：比较评分一致性、重拍稳定性、不同光照/设备条件表现、失败覆盖、延迟与单次总成本。规则版本、来源、评分时间和不可评分原因都保存；不以单一相关系数声称全面可靠。
- D：历史腾讯分数保留来源，不直接覆盖或将新旧分数混排；新模型与腾讯阈值不必同一尺度。模型未达标时不自动给低分拒绝入会，保留复核/重拍与版本回退。

待用户确认：评分是否用于会员准入、是否本人可见/公开、阈值如何确定、申诉复核方式、能否选择不参与，以及是否接受只保留非公开参考评分的方案。**这是规则待定，不是取消用户提出的颜值功能。**业务有后果的最终判定不能信任客户端自行上传的分数。

## 4. 原生自研美颜：可复用什么

当前建议：Flutter 控制交互和参数；原生相机输出帧经 GPU 效果管线后预览/编码，避免每帧全尺寸图像在 Dart 与原生间反复复制。基础候选为肤质平滑、肤色/亮度、滤镜与受控脸部调整；具体效果和默认强度待用户验收，不擅自加换脸或生成身份功能。

MediaPipe Face Landmarker 提供面部关键点/变换数据，可作为效果定位候选，**不是现成颜值模型，也不是整套美颜 SDK**。主仓库采用 Apache-2.0；仍需逐项核查模型权重、依赖、目标平台支持和产品分发条款。[官方能力说明](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)、[官方仓库](https://github.com/google-ai-edge/mediapipe)

PoC 验收：

- 美颜关闭时还原未施加效果的画面；强度可调、预览/导出一致，不随切换镜头失去设置。
- 侧脸、遮挡、多人/无脸时稳定降级，不抖动/乱拉脸；肤色、发丝与背景不过度处理。
- 拍照、录制、相册导入共享参数语义；摄像头旋转/镜像与输出方向正确。
- 中端真机建议先以 720p/30fps 实时预览做预算验证，1080p 和复杂效果再分档；所有数字为提案，不宣称已实现或媲美抖音。
- 前后台释放相机、发热降级、低电量、内存压力、录制中断/来电和空间不足都可恢复。
- 实名/核身素材、拟用于颜值评估的采集素材与美颜作品分离；不能凭 EXIF 或客户端标记证明“从未美颜”。

## 5. 全局媒体压缩要求

用户目标是“画面/声音不劣化、体积合理”。执行口径建议为：**能无损优化先无损；需缩放/重编码的分发副本，以可验收的视觉/听感质量为约束**。已高度压缩的素材无法保证进一步大幅缩小且逐像素/逐采样无损；质量不足时必须保留更高档或提示，不偷偷压糊。

覆盖范围：广告、头像/封面、照片作品、聊天图片/视频/语音、拍摄上传、配乐/合成、游戏媒体及缩略图。核身/审核材料执行独立协议：按供应商格式/质量要求处理，禁止美颜和未经验证的激进压缩；不为了统一体积上限破坏凭证。

| 场景 | 初始候选策略（未批准上限） | 必须验证 |
|---|---|---|
| UI 图标、带文字/透明图片 | 无损 PNG/WebP，合适解码尺寸 | 字体/细线、透明边缘、颜色正确，不能以糊字换体积 |
| 普通照片/头像/封面 | 缩略图与展示图分档，WebP/JPEG 候选；以实际屏幕需求选尺寸 | 纹理、肤色、暗部、放大需求；旋转/色彩配置正确；避免反复有损压缩 |
| 聊天图片 | 默认合理质量展示副本；“原图”能力进入需求评审 | 原图若承诺原始文件必须保持字节完整；隐私元数据处理与原图承诺分开说明 |
| 视频 | 720p/1080p 候选档；H.264/AAC MP4 为兼容候选，HEVC/AV1 后测 | 暗光酒吧、快速运动、HDR/色彩转换、旋转、音画同步；码率不能全场景固定 |
| 聊天语音 | Opus 候选；按清晰语音场景调采样率/码率，确定封装与双端解码 | 弱音、嘈杂背景、头尾不截断、连续播放及听筒/扬声器切换 |
| 音乐/作品音轨 | 选择适合音乐的档位，不直接套低码率语音配置 | 混音/削波/声道/响度与授权范围，试听与导出一致 |

上述不是已冻结规格。每种用途均需配置 `maxInputBytes / maxPixels / maxDuration / targetQuality / maxOutputBytes / codecProfile / policyVersion`；硬上限和默认档位在 D10 确认。验收报告记录输入/输出大小、耗时、峰值内存、设备温度与画面/听感结果，不承诺“统一压到几百 KB”。

### 5.1 端云分工与恢复

- 端上先探测尺寸/格式/时长/方向，在不阻塞 UI 的管线处理；已符合当前策略的输入尽量透传，异常或变大的结果不替换更优原副本。
- 上传前有超限提示、预估流量、进度、取消、失败重试和草稿恢复；断点续传与任务 ID 隔离到当前账号，后台任务受系统限制，不能承诺永不被中止。
- 服务端再次验证实际文件类型、解码后像素/时长、大小和所有权；客户端压缩不能替代服务器限额。受控转码 worker 限内存/CPU/时长/并发，不执行用户拼接的命令或任意下载 URL。
- 云端按用途生成缩略图/展示图/播放档并复用版本化结果。一个上传源生成需要的派生版本，不让每个业务模块都再次压缩；重试幂等、未完成不可公开发布。
- 原件是否上云及保留多久按用途/授权决定；不默认永久留所有原图，也不删除用户相册。私密内容不进公开 CDN，清缓存仅清 App 所有副本。
- 在线内容已有主观质量损失时，不以改容器、压 ZIP 或增加格式转换次数冒充恢复画质。

### 5.2 开源和系统能力候选

以下是候选，不是“已找到全场景最优”的结论。正式采用前锁定版本、可重现构建、许可证/依赖清单和真机基准。

| 候选 | 适用位置与核查结论 | 官方来源 |
|---|---|---|
| libwebp / WebP | 图片有损/无损编码候选；支持透明。具体压缩收益取决于素材，不套用厂商平均数据作为验收值 | [WebP](https://developers.google.com/speed/webp) |
| Opus | 语音编码候选；参考实现 BSD，官方说明可用于商业产品且有免版税许可，分发仍需保留通知等 | [Opus license](https://opus-codec.org/license/) |
| Android Media3 Transformer | 转码/剪裁/效果候选，底层使用 MediaCodec 硬件编解码；设备支持和持续录制管线仍需验证 | [Android 官方](https://developer.android.com/media/media3/transformer?hl=en) |
| Apple 原生媒体能力 | iOS 评估 AVFoundation/VideoToolbox 和 GPU 效果管线；属于系统能力，不冒称开源库，具体导出/实时路径另做 PoC | [Apple AVFoundation](https://developer.apple.com/documentation/avfoundation) |
| FFmpeg | 服务端转码/合成候选；默认 LGPL-2.1-or-later，可选组件影响 GPL 等义务，编解码专利与开源授权分开核查 | [官方许可说明](https://ffmpeg.org/legal.html) |
| FFmpegKitNext | 仅在手机确需复杂处理时评估。旧 FFmpegKit 已退役，但作者 2026-07 公告指向 Next 延续项目；Next 源码分发，默认 LGPL-3.0、启用 GPL 构建则 GPL-3.0。不可照搬已停止维护的旧二进制教程 | [原项目公告](https://github.com/arthenica/ffmpeg-kit)、[Next 项目](https://github.com/arthenica/ffmpeg-kit-next) |

不在本轮安装所有候选。优先选择能满足兼容、质量、成本与商用条件的最小组合；App 不因服务端需要 FFmpeg 就必须捆绑完整 FFmpeg。
