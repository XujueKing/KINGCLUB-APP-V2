# 前后端现代化架构方案

- 状态：**In Review**；以下设计未标“已确认事实”的部分均为当前建议，实施前需 ADR/功能契约批准。
- 已确认用户方向：旧版作为原型和业务证据，允许重构代码及存储过程；延续 UI 不等于延续内部架构。
- 目标：可靠、响应快、可测试、可观察、可逐域交付。不存在未经压测就能保证“更先进、零卡顿”的技术选型。

**2026-09-10 用户方向更新**：[需求台账](REQUIREMENT_INBOX.md)新增全局媒体、微信式聊天扩展、原生美颜、游戏大厅/两款游戏入口、储物券/道具、App 管理能力。**实名核身首版不做，沿用旧照片上传接口方法**；下述新增设计为建议，非已实现。

## 1. 保留与改变

| 层面 | 保留的已确认基线 | 当前建议改变 |
|---|---|---|
| 产品 | 旧版有效业务、视觉语言、会员权益与历史可追溯性 | 故障/权限/空态补齐；新增原生体验经评审 |
| App | Flutter、Riverpod、go_router、现有运行素材和页面资产 | 从页面局部样例迁到按账号隔离的领域状态与 Repository，逐批重构而非整仓重写 |
| 服务 | CCSOP 的安全传输、接口目录、会话、adapter、日志与部署能力 | 增加明确的 KingClub 领域层/可信执行器，完善权限和业务事务 |
| 数据 | U... 统一账号方向、独立 KingClub 实例/库、历史来源映射 | 以新 migration 重建业务模型和约束；旧 k_ 表只作为来源，不照抄设计 |
| 旧 Routine | 可验证的业务规则和回归样例 | 逐项选择保留/重写/上移/废弃，不能一键改语言后就算重构完成 |

不因“现代化”立即替换 Express、MySQL、Flutter，也不先拆大量微服务。需要独立扩容的媒体转码 worker 可与 API 分进程部署；业务领域先在模块化单体内清晰隔离。

## 2. App：界面与状态、I/O 分离

当前建议依赖方向：页面组件 → Application Controller/UseCase → Domain/Repository port；Data adapter 实现 port；运行时装配 Fake 或真实 adapter。`core/shared` 不反向依赖具体页面。

关键责任：

- `SessionCoordinator`：会话快照、刷新 single-flight、顶号/撤销、受保护导航与退出清理。`sessionEpoch` 变化后废弃所有旧账号异步回调。
- `AccountScope`：资料、关系、会话、购物袋、草稿、缓存和本地媒体按账号分区。退出只清 App 所有副本，不删用户相册原图。
- `QueryState`：缓存快照、刷新时间、游标、请求 generation、离线状态；只读数据可先展示缓存再刷新，权益/订单/权限不得由过期缓存授权。
- `CommandState`：提交幂等键、输入快照、待确认状态和恢复查询。禁止通用网络层自动重试支付/发布等写操作。
- `Money`：货币与整数最小单位；金币/钻石数量是不同值对象，禁止与人民币整数分混用。当前 Fake 整数元限制应在真实接入前消除。
- `MediaCoordinator`：活动播放器数量有上限，预加载受网络/内存预算限制，按作品/来源版本隔离回调；返回恢复位置，拒绝隐藏页面晚到播放。
- `NativePorts`：相机、相册、通知、分享、支付、安全存储各有接口与 Fake。手机系统权限在实际任务发生时申请。

本地结构化存储建议采用 SQLite 类方案保存离线会话索引、查询缓存与可恢复草稿；具体 Dart 库、加密与迁移版本在基准测试后选定，当前不强加新依赖。凭据走系统安全存储，敏感审核原图不进入普通媒体缓存。

重构顺序：先守卫/账号边界，再资料/草稿和关系/聊天共享状态，随后 VIP/AA/交易状态与 Money，最后真实 adapter。保留现有 UI 与测试，不同时改视觉、网络、数据模型和路由结构。

## 3. 服务端：沿用 CCSOP，建立领域边界

| 领域 | 唯一事实与业务职责 | 对外端口 / 事件 |
|---|---|---|
| identity/member | 统一账号投影、旧方式照片上传/检测、会员申请/审核与有效资格；KYC 状态独立 | session/member snapshot；membership.changed；首版不接实名核身 |
| social | 好友/关注/黑名单及可见性 | relationships queries/commands；relationship.changed |
| messaging | 会话成员、持久消息、序号、已读/投递、治理 | history/send/ack/sync；message.committed |
| content/media | 作品、评论、可见性、草稿提交、上传/处理/审核 | feed/publish/status；media.ready、work.published |
| club/catalog | 营业日、席位/套餐、库存、AA/VIP、入场/储物 | quote/reserve/party/redeem；reservation.changed |
| commerce/payment | 订单、计价快照、支付尝试、退款与对账 | order/payment/refund status；payment.confirmed |
| wallet | 余额/冻结/金币/券及不可重复账务分录 | ledger/hold/commit/release；asset.changed |
| operations | 审核、代理佣金/会员管理、订台、库存、收银、财务及客服操作 | App 授权工作台与专用权限/审计，可选 Web 补充；普通会员不可调用管理命令 |
| games（新增建议域） | 游戏目录/入口、版本与可用性；《夜幕协议》《修仙世界》的具体玩法另定 | game catalog/launch intent；道具由所属资产域命令消费，不让游戏随意改余额 |

同一业务不变量只在一个地方维护。跨领域通过明确用例/接口或事件通信，不让任意 SQL 随意修改其他域的表。

### 3.1 旧存储过程的重构规则

逐个 Routine 建立“调用方、输入、权限、读写表、副作用、事务、异常、性能、替代方案”记录：

| 类型 | 当前建议 |
|---|---|
| 拼接整页 UI/HTML、动态路由、混合多业务的大过程 | 拆为语义化查询/命令，App 自己组合展示 |
| 登录凭证、第三方回调、网络调用、跨域工作流 | 受类型约束的服务端用例/执行器编排，数据库不承担外部 HTTP 长等待 |
| 金额扣减、唯一核销、并发库存与账务记账 | 明确数据库约束和短事务；由领域 Repository 或受控 Routine 实现，只有一个权威路径 |
| 高效批量修复/导入、复杂集合操作 | 可以保留专门 SQL/Routine，必须有版本、权限、限额和测试 |
| 身份伪造、客户端计价、CSV 权限匹配、隐式奖励/不可追踪副作用 | 不保留漏洞语义；按批准的业务规则重新实现 |
| 无使用证据的过程 | 标记候选退役，检查 Java/任务/回调/动态接口后再决定，不直接删除 |

**需要 ADR 决策的变化**：CCSOP 现有公版文档偏向“核心业务规则在数据库”。用户现已允许重构旧业务，建议新 KingClub 分支采用“服务端领域用例 + 数据库约束/短事务”的分工；凡需改变公版执行器契约，先评审兼容性、目录治理与影响，再新增 migration/测试，不悄然改变所有业务线。

改名、改语言或把一个大过程整体搬成一个大 TypeScript 文件，不算完成模块化。

### 3.2 可信上下文和对象权限必须先落地

- 客户端只提交业务意图，认证 actor 来自验证过的会话。拒绝客户端伪造 `auth/userAccount/roles/scopes/businessLine`。
- 通用 `authPolicy=session` 不替代订单所有权、群成员身份、门店范围、局长角色和资产账户归属校验。
- 业务执行器生成版本化可信 envelope：`params + auth + request`。通用 `db_routine` 的现有 params-only 行为不能直接承接未来业务身份授权。
- Role/Scope 解决可做什么，资源级策略解决对哪个对象可做。群退群、关系拉黑、会员暂停的并发状态必须参与事务检查。
- 受保护附件请求必须证明持有有效凭据，不能只有可见的 ID；私密媒体不暴露长效公开 URL。
- 开放分类目录、接口名字或 WebSocket business 频道不构成用户业务权限；不往全业务频道广播私密消息。

## 4. 契约：语义化 API，不被编号绑住页面

已确认事实：本分支使用 `POST /supper-handshake`、`POST /supper-interface`、K 命名空间及紧凑契约，K101～K107 已登记。早期纯 REST 提案不是已实现事实。

当前建议：保留 CCSOP 传输入口。Flutter 使用 `auth.login / orders.quote / messages.send / content.publish` 等语义方法；K 编号仅在 adapter/目录中映射，不散落页面。新编号由登记流程分配，不在本文虚构已存在的接口。

统一类型契约采用一份可机器校验的 schema，生成或校验 Dart/TS DTO 与 CCSOP 紧凑元数据；OpenAPI 描述传输/专用 HTTP 外壳，业务操作仍需按 operation 逐项建模。不得长期手工维护三套不一致字段。

- 错误区分未登录、无权限、业务冲突、校验失败、限流、未知结果、服务不可用；只向用户展示安全文案。
- 查询统一游标和稳定排序 `(createdDate, id)` 或业务序号，禁止无界全量列表。
- `requestId/nonce` 是单次传输防重放；`idempotencyKey` 是业务命令身份；`clientMessageId` 是消息重试身份；三者不得混为一谈。
- 乐观并发使用 quoteRevision / resourceVersion，接受版本冲突后显式刷新，不偷偷覆盖。

## 5. 状态和一致性

### 交易与资金

订单、支付、退款、账务是独立但相关的状态机。订单取消不等于第三方未付款；支付弹窗关闭不等于订单取消；接口超时不等于事务失败。

建议以服务器订单金额快照创建支付尝试，回调验签并核对商户/币种/金额/单号后，在事务中幂等确认；超时先查单。业务订单、席位/库存、资产冻结、抵扣和奖励的事务边界必须逐用例明确，禁止“先扣钱后靠页面显示成功”。

账务使用追加式分录与受约束的余额/冻结投影；更正用冲正/补偿，不直接改历史流水。每种资产独立单位和不变量，核对期初、收入、支出、冻结、期末与第三方实收/退款。是否采用完整复式科目在财务规则评审中确认。

### 聊天和通知

发送需 actor/member 校验，持久化后分配会话内 serverSequence；以 sender + clientMessageId 唯一去重；已持久化、投递、已读分层表达。WebSocket 仅做低延迟事件，离线恢复按游标补偿；ACK 和重连不能生成重复消息。

群角色变化须即时撤销可见性/发送权限。推送采用不含聊天正文的最小 payload，点击后重新鉴权并读权威数据；通知不能越过当前账号与成员权限。

### 媒体发布

短期上传凭证绑定账号/用途/大小/类型；上传→处理→审核→发布分阶段，状态可查询。处理 worker 与 API 隔离，设置资源/并发/时长限制，验证内容实际类型与输出对象归属。

发布命令必须可幂等恢复；App 退出不意味着服务器任务不存在。取消和重试有明确状态，最终作品可见性由服务端确认。音乐由可信目录 ID 解析与授权校验，禁止客户端任意 URL 驱动下载/合成。

### 事件可靠性

事务内写 Outbox，独立投递到 BullMQ；消费者持久化处理去重/Inbox，处理失败有退避、次数上限与人工补偿。Redis/BullMQ 不作为唯一订单或聊天事实源，不承诺 exactly-once 网络投递。任务重试应得到相同最终业务结果，这也符合 [BullMQ 幂等任务说明](https://docs.bullmq.io/patterns/idempotent-jobs)。

## 6. 数据与部署治理

- 沿用独立 KingClub 服务实例、MySQL 数据库/账号、Redis namespace、日志与发布流程；身份权威服务通过受保护内部接口调用，不直写物业库。
- 新表命名/`rowId/createdDate/updatedDate`/双语注释遵循 CCSOP AGENTS；业务 ID 和旧 ID 建显式映射，不能靠行号相等推定同一用户/订单。
- 表/Routine/接口及分类登记与递增 migration 同批提交；不修改已经执行过的 001～022，后续编号需开工时重新核对，本文不预占编号。
- 变更采用扩展→回填→兼容读取→切换→收缩；新旧 App 混合运行期间版本兼容经过契约测试。
- 开发、测试、预发布、生产配置与凭据分离，敏感日志默认拒绝；审计保存必要 actor/action/object/result，不保存消息/证件/支付响应全文。
- 按领域放量和回滚；启用真实 adapter 需要全局 UI 验收及隔离环境集成验证，生产切换另行确认。

## 7. 架构验收

必须证明：跨账号/跨店/退群访问被拒绝；并发下单不超卖；重复命令/回调不重复记账；网络未知结果可恢复；断线消息不丢不重；旧新数据可对账；崩溃不串账号；性能在目标真机与明确负载下达到 [预算](UI_AND_PERFORMANCE.md)。

模型使用偏好为用户指定 GPT-6 Astra；[官方模型文档](https://developers.openai.com/api/docs/models/gpt-6-astra)已核对。当前工具未提供主会话模型标识核验/切换操作，本轮不声称已执行模型切换；指定模型需由会话侧确认。本轮未在产品中新增 AI API、费用或凭据配置，也不以模型名称替代架构评审和验证证据。

## 8. 09-10 新需求的架构影响（当前建议）

### 首版照片准入，不接实名核身

沿用 `/kingclub/registrationPhotoUpload` 的上传/暂存令牌业务方法，迁到 CCSOP 的可信会话及受控媒体链；后续检测/评分/会员审核以匹配旧版的契约重建。令牌绑定 actor、imageType/用途、有效期与消费状态；校验真实 MIME、大小/像素、归属和重放。是否保留旧兼容路径在 R1 冻结，不让 Flutter 复制旧共享 Basic 凭据。

建议 `RegistrationPhotoPort`、`AppearanceAssessmentPort`、`BeautyEffectsPort` 分开。真实实名核身 port 如已有设计只留后续扩展，不在首版装配 SDK、发起权威核身或阻塞注册。照片已上传、检测/评分结果、会员审核、KYC 分别建模；会员通过不得自动把 U...身份投影改为 KYC verified，也不覆盖历史可信证据。

自建颜值模型先隔离验证，保留算法来源/版本/评分尺度、不可评分状态与复核，未达标不替换既有腾讯评分。任何有准入后果的评分以受控服务端结果为准，不能信任手机上报分数；美颜与准入素材分离。详见[技术调研](MEDIA_AND_FACE_RESEARCH.md)。

### 统一媒体处理

每种用途一个版本化 `MediaPolicy`，包括输入上限、像素/时长、质量档、编码与保留策略；`MediaAsset` 记录来源、所有权、输入/输出摘要和派生关系。端上原生编解码/GPU 负责拍摄和合理体积，云端受限 worker 负责验证及必要分发档，复用已有 MediaCoordinator 控制播放。

聊天语音、照片/视频作品、广告、头像、游戏媒体共用基础管线而不共用全部权限；审核照片有独立用途/存储权限，不公开发布。照片/音轨不能无限重复重编码。选型与硬上限经质量/体积/耗时/耗电/许可证测试再冻结，不以“开源最优”代替证据。

### 微信式聊天与业务卡片

在现有消息模型增加版本化 typed payload 的设计评审：礼物、付款、AA、游戏邀请、推荐各自有受控业务引用，旧客户端有安全降级。卡片只展示/导航，不直接携带可信价格、钱包扣款权限或游戏管理员权限；打开后重新查归属/状态。群收款与 AA 预订分享的语义待定，不能直接当同一交易类型。

### 储物箱与游戏入口

储物箱是多资产的统一展示投影，不把酒、团购券、赠券、游戏道具压成通用字符串或统一现金余额。酒/券/道具各有来源、剩余数量、有效期、冻结与使用记录；消费以所属域事务/幂等命令执行。游戏引用目录注册 ID 和兼容版本，不下发任意代码/URL；具体游戏引擎、房间状态和同步协议等到玩法规格确认后设计。

### App 授权管理与领域事实

管理员工作台可与会员界面在同一个 App，但 Repository、路由守卫和服务端操作权限分离。角色与门店/代理所属会员范围同时检查；角色变化即时撤权。员工代订记录 actor 和受益会员，不能冒充用户会话。

代理佣金按来源订单、规则版本和归属快照计算，退款后幂等冲回。订台和库存复用消费者交易所用的权威席位/库存；收银不另建一套可随意改的支付状态；财务从账务/结算事实出报表，更正须冲正和审计。费率、审批、交班和结算规则待用户确认，不能写死为旧代码样例。
