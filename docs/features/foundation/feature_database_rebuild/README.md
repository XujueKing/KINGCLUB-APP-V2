# 数据库重建与旧数据迁移

- 文档状态：In Review
- 所属业务域：foundation / data platform
- 当前阶段：资产盘点与目标设计
- 最后更新：2026-08-24

## 目标

建立可由 migration 从空库重复构建的 KingClub V2 MySQL 8.4 数据库，并把旧 `k_` 数据按身份、社交、消息、内容、门店商品、订单和资产域受控迁移。

## 已确认事实

- 旧结构文件共有 515 张表，其中 `k_` 业务表 94 张、1,484 个字段。
- 94 张 `k_` 表没有数据库外键。
- 常用表普遍只有 `rowId`、业务 ID 和 `indexed` 索引，缺少按真实查询链路设计的组合索引。
- `k_user` 同时混合登录凭据、手机号、身份证、个人资料、会员状态、偏好、推送和在线状态。
- 聊天成员、关注集合和部分已读数据使用 LongText/逗号集合，不能直接作为 V2 关系模型。
- 旧表使用 MySQL 旧式整数宽度、部分 `utf8` 字符集和大量数字状态枚举。

## 范围

### 包含

- 94 张 `k_` 表清单与领域归属。
- 第一批身份/登录表的字段映射。
- 新旧 ID 映射、全量迁移、校验、增量同步和回滚方案。
- 新库 migration、目录登记、双语注释和数据治理要求。

### 不包含

- 本阶段不创建生产数据库。
- 不直接修改或导入旧结构文件。
- 不在一次迁移中重建全部聊天、交易和内容业务。
- 不迁移真实人脸、证件或支付数据到开发环境。

## 当前建议

- 在同一台服务器上新建独立 KingClub V2 数据库和服务实例，旧库作为只读 source system。
- 新库先安装 ccsop-service 的公版 migration，再按领域增加 KingClub migration。
- 用户基础模型复用物业公版结构和安全语义，物业公共用户表暂时作为统一账号权威源。
- KingClub 注册时通过内部身份接口取得统一的 `U... userAccount`；KingClub 数据库不得自行生成用户编号。
- KingClub 先注册时，物业公共用户表写入账号、手机号身份和真实状态的实名占位/摘要，但不创建物业业务成员或权限。
- 新表使用 camelCase、`rowId`、`createdDate`、`updatedDate` 和双语注释。
- 第一批只建设身份、App 成员关系、旧 ID 映射、登录挑战和会话所需表。
- 交易金额使用明确精度和不可变流水，不把钱包当前余额作为唯一对账依据。
- 聊天参与者、消息已读、关注和黑名单全部正规化为关系表。

## 页面清单

本功能没有 Flutter 页面。数据库设计完成后，登录功能可建立登录相关页面目录。

## 风险

- 旧数据缺少外键，存在孤儿记录和一对多字符串集合。
- 身份证、手机号、人脸和支付信息属于高敏数据，迁移需要单独审批、加密和留存策略。
- 钱包、订单、支付和退款必须做金额对账，不能只比较行数。
- 旧业务 ID 长度 255，新平台 ID 长度 64；映射时不能截断或直接强转。
