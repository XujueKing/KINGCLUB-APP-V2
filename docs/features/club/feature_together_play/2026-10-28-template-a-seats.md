# 主题派对模板 A 与真实选座

用户本轮明确要求直接实施 UI、服务端及数据库；本文件记录已实现规则。覆盖早期“超过10人”和商家盲盒分座的相关描述。iPhone 仅在用户明确命令后构建，本次只打安卓包。

## 卡片与详情

- 已确认报名少于10人：发起者48点头像、门店名或昵称、小字介绍。商家取门店LOGO，合作者取个人头像；商家没有独立介绍字段时，使用已审核活动的场地说明，不虚构门店介绍。
- 达到10人：底栏切换10位真实报名会员，28点头像、每行5个共2行，横距6、行距4；有本人时优先纳入，不制造报名者。缺照片保留男女图标。
- 卡片原位展开动画保留：只有海报随矩形放大，底栏、头像、文字、按钮保持逻辑尺寸。
- 详情增加所选卡座小卡片：上男下女，空位男女图标、已报名实际照片，无照片用男女图标。点击真实会员链接到既有公开资料页，继续受该页隐私权限限制。
- 支付中的座位变暗且不可选择；只有付费确认会员公开头像。空位不是已报名，报名不是已核销。

## 发布、报名和调座

商家在既有发布流程选择店内真实编号卡座/包厢，可全选或部分选。沿用门店、套餐、素材审核、年龄颜值等资格规则。合作者受既有整月签约桌台权限限制；本次没有向普通会员开放任意发布。

每场最多30个位置、每个物理位置最多100席；详情返回当前活动实际预留份额，总人数不超过位置容量。已配置男女比例时，按累计比例分配到各卡座；未配置时不额外强加50/50名额，已报名男女仍分别展示。未配置比例的空位允许任意性别选择，付款后按实际性别展示。

进入报名先选“系统随机”或“自己选座”，自选包含卡座引用与具体席位。未付款只保存订单意向，不占座、不发券。实际付款共用原资格、价格、券、金币和余额/微信链路；精确分座在同一数据库事务内执行，冲突先回滚再提示重选。微信付款中占座，取消后在后续分配时释放；不得通过客户端覆盖价格或已确认座位。

付费分配后只能申请调座，填写原因；发起人或所属门店经营主体负责人在活动详情批准/拒绝。批准前原座位保持；批准时重查名额、性别、核销状态和冲突。请求及审核可幂等重试；每次展示最多30条待处理申请，处理并刷新后继续出现后续申请。已核销不能调座。原收银分桌入口不允许绕过本活动精确席位审核。

## 接口与兼容

- K261004001985：Today列表，沿用 `kingclub_together_feed`，增加真实发起人头像/简介。
- K261004001986：一次活动详情包含桌台与席位；`seatAction=requestChange/review` 同入口承接独立申请/审核动作，对应 `kingclub_activity_seats`。
- K261004001988：保存 `seatChoice` 未付款意向；付款服务在原事务内调用 `kingclub_activity_seats(action=claim)`，不另外开付款事务。
- K261008002052：既有发布工作台、报价及发布，`kingclub_party_publisher` 统一校验位置池和签约权限。
- 收银读取继续用 `kingclub_together_seats`，优先精确席位所属桌台；核销过程认可该实际位置。批准调座后发原有桌台变更事件。

旧日期日历、旧入场券和原财务流程保留。无物理位置的历史活动维持原报名兼容路径；新发布必须选择真实位置。历史已付但无法还原物理席位时阻止新分座并提示商家核对，不覆盖旧订单。
