# 普通文字优先使用已连接的可信中继

实际单聊页面现在向控制器提供动态路由判断：存在当前 NovoRUDP 中继连接时，普通文字先尝试成员中继通道；未配置或未连接时仍直接请求 CCSOP。中继发送最多等待 3 秒，失败继续原服务端路径，本轮不重复尝试中继。

中继发送仍通过设备目录检查双方权限及设备绑定。引用消息与媒体不走此文字通道。收到对端持久化回执后立即更新显示，并保存 `peerDelivered`；服务端历史同步使用原 `clientMessageId`，直到服务端确认才移除待同步记录。已取得对端回执的重试不再次发给中继。

当前是“中继优先交付，服务端同步历史”，不是无服务器聊天，不减少服务端文字历史存储。中继尚未连通时不会启动一次额外等待。超时底层请求可能稍后完成，仍依靠相同编号去重。尚未实现本次路由的媒体直传或公网自动打洞。

验证：25 项控制器/登录重绑定测试通过，包括优先发送顺序、相同消息编号、对端先确认时显示送达、失败回退、服务端离线后保持待同步、禁止重复中继发送、离页后迟到回执不能继续发送。控制器测试使用接口替身，不能代替双机网络验收。修改的 3 个 Dart 文件静态分析通过。

当前预览 APK 未配置可信中继地址，本次源码未安装手机；需配置真实测试节点并完成 A/B 测试后，才能认定双通道切换交付。

## 真实 SUPERVM 中继验证

后续使用本机 `novovm-product-relay.exe`、固定公钥与 TLS 证书、真实 Windows 原生 DLL、两个独立身份及 SQLite 文件运行了 `member_relay_runtime_test.dart`。分别验证服务端失败后中继发送、中继优先发送；两项均通过，静态分析无问题。

中继优先用例在调用服务端替身前检查接收端 SQLite 已存在消息，避免仅凭调用顺序认定送达。两种路径还覆盖发送回执、重复编号去重、接收页面刷新、已读回执、服务端记录合并、前后台断开重连及关闭时忽略迟到目录查询。

此测试的数据链路是真实 SUPERVM WSS，本地持久化及原生加密也是真实实现；会员授权目录与 CCSOP 消息接口仍使用测试替身。测试只绑定本机回环地址，不证明真实会员授权、手机局域网或公网可达性。原生握手与传输所用临时身份未提交到 Git。
