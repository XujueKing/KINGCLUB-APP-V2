# A/B 互相关注与通讯录实机核验

## 范围

使用现有 A/B 测试会员和正式包 `com.lingmei.kingclub`，沿用当前已安装的 profile 包。仅操作已授权的两个测试会员；没有清数据、卸载、直接更新数据库或操作第三台设备。

## 实测过程与结果

- B 的 A 资料页显示“已关注”，A 的 B 资料页显示“关注”，与此前服务端单向关注结果一致。
- 在 A 资料页正常点击“关注”后，按钮显示“互相关注”，B 的粉丝数从 0 变成 1。
- 两端返回通讯录，无手动下拉刷新，均显示对方“徐珏”。A 原有另一位联系人也保留。
- 分别强制结束正式包进程、重新启动、进入消息和通讯录，两端仍显示对方，登录保持。
- 最后只读核对服务端 A/B pair：`lowFollows=1`、`highFollows=1`、`lowBlocked=0`、`highBlocked=0`。查询前确认设备绑定表只有两个不同会员，输出未包含凭据。

## 结论与限制

当前“互相关注成为好友→双端通讯录显示→在线冷启动保留”通过。这里的冷启动保持网络连接，不替代离线本地快照验收，也没有帧级证明首屏完全无加载。

本轮没有重新扫码或重新接受好友申请，不能据此认定扫码路径已经复测通过。历史 accepted 申请和此前单向关系为何并存，尚未定位；本轮通过正常关注操作恢复了 A/B 互相关注，没有将历史问题归因于用户取消关注。

本机采集位于隔离构建目录 `build/contacts-462606d8.xml`、`build/contacts-TOHYQSINONBMJN6H.xml` 和对应 `contacts-restart-*.xml`，不提交包含设备页面数据的原始转储。

## 仅聊天设置与关注隔离

继续核查当前代码：客户端详情页仅调用 settings 的 onlyChat 字段；服务端 settings 更新 kingclubChatMemberState，不更新 kingclubDirectPair 的关注字段。扫码 pending 申请首次接受会同时设置双方关注；相同 accepted 请求重放只返回当前状态，不强行重新关注。

实机初始双方 onlyChat=0、双方关注为 1。在 A 的聊天详情中开启“仅聊天”，服务端只读查询确认 A onlyChat=1、B onlyChat=0，双方关注仍为 1。B 重新进入 A 的资料页，作品、动态、相册三个分类均显示“暂时无法查看”，互相关注与私信入口保留；点击私信可进入会话，原历史可见，输入框 enabled=true。本轮没有额外发送消息，因此这里只证明聊天入口及输入可用，不扩大为一次新的发送送达验收。

随后通过 A 原开关恢复 onlyChat=0。B 返回通讯录后重新进入资料页，内容区恢复“暂无作品”，互相关注保留；服务端确认双方 onlyChat=0、双方关注仍为 1。恢复完成，没有保留测试隐私设置。

这排除了当前这一次“仅聊天”操作导致取消关注，不能证明旧版本或所有历史操作均无问题。测试账号没有作品，本轮验证的是访问状态切换，不是已有作品媒体的隐藏/缓存撤权全链路。历史关系变成单向的根因仍未定位。

## 接受申请提示与实际关系一致

复核当前服务端：首次接受 pending 扫码申请在 pair 锁定事务内同时写入双方关注；相同 accepted 申请重放返回当前 `friends`，不会覆盖之后明确改变的关注状态。现有 SQL 集成用例覆盖五次并发接受和取消关注后重放，但本轮仅阅读这些用例，没有重新执行 SQL 集成测试，也不据此认定历史原因。

发现并修正客户端提示缺口：此前忽略 resolve 的返回值，只要请求未抛异常，就显示“已互相关注，可以聊天了”。现仅在 `status=accepted` 且 `friends=true` 时显示该提示；`friends=false` 明确说明申请已处理、当前未互相关注；关系字段缺失时仅提示检查当前关系。仍刷新申请、通讯录及角标，不自动补写关注，不改变实际关系。

验证：`flutter test test/real_friend_requests_test.dart test/local_relationship_sync_test.dart` 共 8 项通过，覆盖三种关系返回值及无实时连接时的通讯录/角标更新；两个修改文件的 analyze 通过。本次为源代码修正，尚未覆盖安装到 A/B，不算扫码双机复验通过。
