# 同服务器不同目标端口的实际映射观察

保持 A 移动网络、B 家庭 Wi-Fi。Android shell UID 诊断 socket 先向自有
STUN UDP 3478 获取映射，再从同 socket 向服务器既有 UDP 41000 发三个
随机 16 字节诊断包，最后回查 STUN。服务器限时抓取，只匹配此次随机标记，
比较实际来源与 STUN 映射；不输出端点、token 或报文内容，不写抓包文件。
没有增加监听服务、修改安全组或防火墙，手机临时 dex 已清理。

| 对照 | 服务器实际收到 | IP 相同 | 端口相同 | 回查 STUN 映射稳定 |
|---|---|---|---|---|
| A → 3478 正向校验 | 是 | 是 | 是 | 是 |
| A → 41000 | 是 | 是 | 否 | 是 |
| B → 41000 | 是 | 是 | 是 | 是 |

这直接证明本次 A 的映射会随目标端口改变，而不是仅凭收不到回复推断。
先前不同服务器的测试还观察到 A 的公网 IP 也会改变；不能将本次同 IP
结果推广成对任意目标均保持 IP。B 的结果仅覆盖已测试目标，不等于完整
NAT 类型认证。实际聊天的公网 UDP 直连仍未通过。

配套 A 主动发包前后实验：beforeOutbound=false、afterOutbound=false，
baselineAfter=true、mappingStable=true。结合本次直接捕获，说明原 STUN
映射不能直接视为另一目标端口的映射，但仍不定位具体哪一层 NAT 或过滤器。

诊断开发中的未校准结果没有用于上述结论：初始 AF_INET 抓取不能完整覆盖
Docker 转发，改用 AF_PACKET 后还需按 UDP 长度排除以太网填充；正向 3478
校验通过后才采纳最终结果。所有初始 received=false 均按不确定处理。

当前需要的是目标相关映射下的候选发现/穿透策略，继续缩短探测间隔不能
补出未知端口。本节点只增加可复用的测量工具，没有修改业务或 SuperVM 共识。
