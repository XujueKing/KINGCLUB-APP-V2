# 长时间后台消息接收（2026-09-28）

用户明确要求补齐长期后台保活，同时修复后台新来电与离线推送。采用用户可见、可停止的 Android specialUse 前台服务，真实用途是已登录即时通信的持续接收；不冒用麦克风、播放或 dataSync 类型。类型和用途须如实提交商店审核，不能承诺系统永不回收。

服务拥有独立 FlutterEngine，复用加密实时协议、当前安全会话和通知收件人校验。UI 前台由 UI 连接接收；UI 后台由服务连接接收。服务重建重新读取安全存储，退出账号停止，不把凭据放 Intent、日志或普通偏好。未登录不启动，用户停止后不自动重启，设置中可重新启用。通话服务仍只保护已接通的真实采集；新来电通过接收服务验证并通知，不能自动接听。

系统强制停止、厂商冻结或真正断网仍需恢复或厂商推送，不能把 START_STICKY 作为送达保证。后台周期核对未结束邀请，减少事件丢失导致的漏来电。实机持续锁屏、进程回收恢复及厂商离线送达需分别记录。

边界补充：用户在系统设置里“强行停止”后，不承诺厂商推送能重新唤醒，需重新打开应用；这与普通系统回收、最近任务划掉页面不同。

依据：https://developer.android.com/develop/background-work/services/fgs/service-types

## 通知点击错误页修复

用户报告的“花屏”已从 B UI dump 确认是 Page Not Found / GoException。旧通知用 kingclub://notification/… 区分 PendingIntent，Flutter 自动深链将其交给 GoRouter，和受校验的 ChatPushOpen 跳转竞争，导致错误页及返回异常。

新通知改用显式 Intent action 区分身份，不携带合成深链；MainActivity 在冷启动、onNewIntent 交给 Flutter 前移除旧版内部通知 URI，保留原始推送 payload，由既有账号、有效期和会话校验决定跳转。未放宽校验或添加任意网址路由。

B 覆盖安装后，实际 A→B 新消息通知点击进入正确会话，返回到聊天列表，UI dump 无错误页。20 项 push-open runtime/recovery 测试通过，最终 Kotlin 增量 Profile 构建通过。A 同步覆盖安装此修正版。

## 断网恢复后的未读提醒

修复服务重连只补查来电、不补查未读消息的问题。真实 connection.ready 后分页读取授权会话状态，补出未读私聊/群聊通知，过滤已读、免打扰和自己发送的最后消息；与实时事件共享按账号、会话、序号去重记录。20 秒来电检查改用独立事件，不周期全量扫描未读会话。分页请求失败或期间失效不消耗之前页的去重记录。

去重记录仅在当前接收器生命周期内有效；进程重建后可重新提示现存未读，通知仍按会话标识替换。此方案不是持久化逐条推送回执，也不保证厂商通道送达。

11 项测试通过，包括 300 会话分页后重连不重复、实时事件与补查去重、免打扰/已读/本人过滤，以及失败和失效后重试。相关代码 analyze 无问题，Profile 构建通过。

实机 B 关闭 Wi-Fi（无移动数据），A 发送 AB_OFFLINE_RECONCILE_0928 后恢复 B Wi-Fi。05:50:07 重连 connection.ready 后出现两次 localShown=true，系统活动通知列表确认私聊与原有群聊未读通知；没有依赖对应新消息实时事件来触发。测试已恢复 B Wi-Fi，A/B 均覆盖安装此版本，保留账号数据。

## 来电优先与任务划除（后续节点）

后台消息查询与来电检查改为独立串行队列。重连分别提交未读补查和来电检查，消息分页慢或失败不再阻塞来电；来电自身保持顺序，前台恢复/账号失效仍通过 epoch 与安全会话检查丢弃迟到处理。

13 项通知/未读恢复测试通过，包含阻塞未读查询期间私聊和群聊来电仍被处理、排队来电在回前台后失效。测试不要求两个独立队列的首条执行顺序，只验证无互相阻塞及同队列顺序。相关 analyze 无问题，Profile 构建通过。

B 锁屏状态，A 发起视频通话：05:57:37.593 收到 chat.call.changed，05:57:37.753 localShown=true；系统活动通知确认 call 类别。A 挂断后活动来电通知数为 0，B 电源状态仍为 Asleep。本轮验证的是后台视频来电通知及取消清理，不是本次接听后的双向画面/声音。

仅划除 B 当前聊天应用的最近任务卡片后，进程和接收服务仍存在。A 发送 AB_TASK_REMOVED_RECEIVE，06:02:11 收到事件、messageEligible=true、localShown=true，系统活动消息通知可见。此证据不能替代“进程真的被系统杀掉后重建”的验证。

厂商衔接复核：服务端仍按前台心跳暂缓普通推送，后台本地通知尚无逐条服务端送达回执；因此不能声称后台接收后一定不会再收到厂商提醒。厂商普通通道的夜间管控仍是已确认外部限制，未修改业务分类或盲目重发已受理推送。

## 本地通知失败后的补发资格

后台实时消息与断线未读补齐现在仅在原生 show 返回 true 后记录已提醒序号。返回 false、平台异常、提交期间回前台或账号重置均不提前消耗序号，下一次有效事件或重连可重新补齐。前台横幅原有行为保持。系统接受通知不等于用户已看到通知，也不等于厂商推送送达。

验证：16 项通知解析及后台队列测试通过，覆盖失败后重试、成功后实时/重连去重、异常和账号重置后的迟到回调。该节点不修改服务端推送抑制逻辑；厂商通知与本地通知跨通道去重仍未完成。此次尚未重新打包安装，不将代码测试记为真机验收。

## 本地通知回执跨通道去重

后台原生 show 成功并再次确认当前登录/后台状态后，通过既有认证加密 WebSocket 发送 client.messageNoticeShown 或 client.callNoticeShown。消息带 scope/conversationId/sequence，来电带 scope/callId；不发送正文或将消息标为已读。发送与前台心跳共享串行队列，防止异步加密使序号乱序；换会话/连接时丢弃旧发送。未成功提交本地通知时不回执，断网丢回执仍保留服务端兜底。

服务端按设备 session 匹配 pending delivery，消息只覆盖当前通知对应序号及之前消息。有效回执跳过对应厂商发送；新的通知最多约 2 秒等待窗口，无回执继续厂商路径。进程内回执 120 秒/最多 10000 条，不声称分布式恰好一次或能撤回已经交给厂商的通知。

20 项客户端定向测试、静态检查通过，profile 构建及 A/B 覆盖安装成功。服务器必要文件已部署，runtime 检查及配置保留比对通过。A 发消息后 B 本地通知成功、服务器回执 accepted，对应 push delivery skipped / LOCAL_NOTICE_SHOWN / attempts=0；语音来电同样确认 call delivery 跳过厂商，测试已挂断。登录保留、没有卸载或清数据。

仍未完成：系统回收后的可靠通知、长时间后台验证、iOS APNs/PushKit/CallKit，以及新发现的通话占用残留核查。跨通道去重已实现并双机验证，但超时/断线/多实例或厂商已接受时仍可能重复。

## 通话占用核对纠正与通知通道关闭

再次按 callId/groupCallId 检查：3 条 occupancy 行的两个通话引用均为空，实际单聊占用 0、群通话占用 0。该表保留用户锁行用于并发互斥，不能把 COUNT(*) 当作正在通话，也不应删除这些行。此前“占用残留”判断撤回，不再作为待修故障。

修正本地 show 成功条件：除应用通知总开关外，Android 8+ 检查具体消息/来电通道 IMPORTANCE_NONE，Android 9+ 检查通道组是否阻止。关闭时返回 false，不记录已提醒序号、不发送成功回执。保留用户通道设置，不重建通道 ID 或强制开启通知；低重要性/静音通道仍可显示通知，不误判成禁用。不保证系统收到 notify 后必然展示横幅或发声。

验证状态：Android preview/profile 原生构建通过，B 覆盖安装成功；临时关闭再恢复消息通道，允许通知、静默、横幅/锁屏、铃声、振动设置与原截图核对一致。A 从 offline 重连后变为 unauthorized，未安装此原生增量；双机关闭通道发送用例尚未完成，不声称真实回执验证通过。
