## 消息与数据规则

- 客户端先写本地持久 Outbox，再发网络请求；重试复用同一个 clientMessageId。服务端以会话、发送方、clientMessageId 唯一约束去重，并验证重复 ID 的内容一致。
- 服务端事务同时写消息、会话序列和事件 Outbox。只有持久化成功才确认 accepted；delivered/read 必须有目标设备/会员回执，不能用 WebSocket 连接成功代替。
- MySQL 保存业务事实；Redis 只承担在线状态、速率限制、短期路由和扇出。断网后以持久游标补收，不依赖 Redis Pub/Sub 保存历史。
- 分页与补收使用不透明游标；服务端序列属于具体会话/传输，不把服务器时间、链高度作为全局消息顺序。
- 群已读、成员变动、为我删除、撤回作为版本化事件；撤回不能保证对方未截图或已下载文件被远程销毁。
- 媒体采用上传意图、已验证媒体引用、缩略图、限时授权读取；聊天消息不能提交任意外部路径。本机缓存按会员隔离。
- 现有 WebSocket 是客户端到服务端加密，不是端到端加密。端到端加密需成熟协议、设备密钥生命周期、换机恢复和群密钥方案，不能自行拼装或提前宣传已具备。

## 主网与通话边界

界面依赖 ChatRepository；ChatTransport 负责消息提交/同步，ChatMediaStorage 负责附件，ChatIdentity 负责身份和设备证明，CallSessionPort 负责通话生命周期。现有 CCSOP 与未来主网分别实现适配器。

- 用户已提供 D:/WEB3_AI/SUPERVM，当前 HEAD 27e9dee1。已读取 NovoRUDP FrameV0、修复窗口、传输边界、跨机性能记录及 reachability 实现。移动端 SDK、设备签名绑定、密钥恢复、离线信箱、附件持久性及聊天投递语义仍需逐项验证。接口存在不代表兼容性验证完成。
- 默认不把聊天正文、实名、定位、音视频写上公开链；链身份只作经过验证的账户绑定。链上资产交易与即时消息时序分开。
- 实时音视频使用 WebRTC 媒体传输；信令、鉴权、呼叫状态存储和可用中继仍要实现。首期准备自建能力，不默认购买第三方套餐。群通话需评估 SFU 带宽和机器容量。
- “无服务器化”目标是可替换中心协调与存储依赖，而非承诺不需要在线节点。手机被系统挂起、离线收信、NAT 穿透失败都必须有可验证的处理。
- 任何主网接入先跑与 CCSOP 相同的去重、权限、补收、取消、过期和重放契约测试，能力缺失明确禁用，不用降级掩盖。

接入判断：优先作为可靠消息、录音文件及附件的候选传输；仍需通过手机 ARM64 桥接、鉴权加密、MTU/分片、进程恢复、离线邮箱以及双端契约验证。

FrameV0 的 SHA-256 checksum 是完整性校验，不等价于端到端加密或身份认证。仓库其他层有认证代码，接入时要追到实际生效路径，不能仅凭字段推断安全保证。

实时语音/视频单独验证：过期音视频帧需要截止时间策略，不能无限等待可靠补包；本轮查看的 NovoRUDP 核心未找到完整音视频抖动缓冲/自适应码率证据。继续保留 WebRTC 媒体实现接口，后续只有 NovoRUDP 实时策略实测达标才替换。录音消息是可靠文件，和实时语音通话分开。

下一组公平实验：相同机器/网络/报文尺寸/加密级别，对照 NovoRUDP、TCP/TLS、QUIC；测空载/满载消息P50/P95/P99、有效吞吐、重传放大、0/1/5/10%丢包、20/80/200ms RTT、乱序/抖动、移动网络切换、CPU/内存/耗电。现有记录没有完成这个对照，不能宣称全面快于成熟传输协议。

### 压缩与人声处理追加要求

用户要求成熟压缩与去杂音。当前录音配置启用设备支持的 noiseSuppress、echoCancel、autoGain，并使用 Android voiceCommunication 音源；具体效果取决于系统实现，不保证设备全部支持，也不视作已完成 WebRTC 通话降噪。酒吧强音乐环境、耳机/扬声器和人声失真须真机试听，避免系统处理与软件降噪重复叠加。

压缩目标按媒体分层：结构化文字/历史以 Zstandard 作为待评测候选，小消息不因压缩增加延迟；语音通话评估 Opus，当前录音已使用 AAC-LC；图片保留原图，适配WebP/JPEG等双方支持格式；视频按硬件与双方能力协商H.264/HEVC/AV1，不强制所有手机软件转码。既有压缩媒体不盲目再压。格式协商、压缩后大小比较、解压大小上限和先压缩再认证加密都须纳入契约；这些传输压缩尚未接通，不以本段设计代表完成。

依据： https://facebook.github.io/zstd/ ，https://developer.android.com/media/platform/supported-formats ，本机 record_android/AudioEffectsManager.kt。

### 2026-09-13 好友主页与私信规则（用户最新确认）

- 点击头像查看对方主页沿用旧小程序 `pages/chat/chat.js:833` → `pages/userInfo/userInfo` 的抖音式布局：封面、头像昵称、账号、关注/粉丝统计、签名标签、关注/私信按钮、作品/动态。新版仅展示新版真实资料和内容，不导入旧会员数据，也不展示本人私有实名字段。
- 互相关注即好友，不再要求独立的加好友审批才能建立好友关系。关注单向保存，好友身份从双向有效关注推导。
- 用户追加确认：扫码加好友申请仍保留；由对方通过时，在同一事务中建立双方关注，成为同一种互关好友。扫码/提交申请本身不算通过，不能替对方关注。双方互关与扫码通过共用好友投影和私信许可。
- 用户追加确认“仅聊天”：本人对某好友设置后，该好友仍可聊天，但不能看本人的作品、日常等内容。此权限是方向性的内容访问限制，不删除好友、不自动取消关注；主页列表、单条内容直链、附件授权均须校验。恢复可见需要本人修改设置，好友不能替本人解除。已有本机媒体缓存还需在权限变更/账号切换时失效，不能只隐藏主页入口。
- 单向关注只允许发出一条未获回复的私信。接收者无需先关注即可回复；真正回复后允许继续聊天，但这不自动建立互关好友关系。
- 额度作用于账号对，不作用于设备或本地会话。未读/已读都不是回复；重试复用 clientMessageId；删除会话、取消再关注不能重置已发证据。拉黑优先于聊天许可，解除拉黑不重置邀请记录。
- 按上述“一条信息”理解为跨消息类型共用额度，后续图片/语音/附件必须走同一服务端许可检查，不能每类各发一条。群内消息有独立成员权限，不能借群邀请绕过私信限制。
- 当前已开始实现服务端纯规则和发送事务契约；尚未接入 MySQL、超级接口和手机 UI，不能称规则已上线。下一步落地账号对锁、消息幂等唯一约束、持久发送证据以及关注/拉黑与发送使用同一事务锁。
