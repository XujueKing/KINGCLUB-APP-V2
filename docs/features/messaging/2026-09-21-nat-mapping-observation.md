# A/B 同 socket、不同目标映射对照

保留 A 移动数据、B 家庭 Wi-Fi。2026-09-21 用 Android app_process 执行独立诊断，同一个 IPv4 UDP socket 依次向自有 STUN 与 Cloudflare 公开 STUN 发 Binding Request，再回到自有 STUN。两次执行均收到所有响应，并且首次/末次自有 STUN 映射一致。

第二次执行增加 IP/端口分项比较：

| 设备 | 首/次/复测响应 | 原目标映射稳定 | 跨目标 IP 相同 | 跨目标端口相同 |
|---|---|---|---|---|
| A | 全部成功 | 是 | 否 | 否 |
| B | 全部成功 | 是 | 是 | 是 |

这直接证明诊断流在 A 上存在目标相关的映射差异，不能将其 STUN 映射当作向所有对端发送时都相同的地址。未输出具体公网地址、端口或身份信息。手机临时 dex 已删除，未更改网络、路由器或服务器配置。

限制：该实验使用 shell UID 和单独 socket，不是聊天 socket 抓包；不能仅据此区分差异来自运营商 NAT、设备网络策略或其他中间设备，也不能判定 B 的入站过滤规则。B 的两目标映射一致不证明所有目标都一致。该证据未证明公网打洞绝对不可能。

后续代码审查重点：当前接收策略允许已通报 IP 的新端口，但完全未通报的 IP 在 AEAD 验证前被丢弃。A 的公网 IP 随目标变化时，若报文能抵达，这一限制可能阻止认证后的 peer-reflexive 学习。不过当前聊天计数 unknownAddresses=0，尚未证明实际有此类报文抵达，不能将放宽 IP 学习直接宣称为本次问题的修复。需要继续核对实际候选与入站过滤，保持端到端认证和有界探测，不扫描任意端口。
