# 双机文件删除与持久化清理

仅使用 A/B 两个授权测试会员，第三台设备未操作。两端沿用已安装正式包 com.lingmei.kingclub。新建专用文本文件 AB-Cache-Delete-0927.txt，11702 字节，不包含用户资料，通过 A 的「更多 → 第二页 → 文件」正常选择、确认发送。

系统文件选择器的下载目录搜索出现“暂时无法加载内容”，改用设备存储根目录搜索后选中；这不是聊天上传失败。

## 实际证据

- A 确认发送后，B 会话出现 11.4 KB 文件卡片。B 打开并点击读取，页面明确显示“下载完成，文件校验通过”。
- 在 B 应用私有目录发现对应加密下载缓存的 0.block 和 retained。通过该新消息的字段计算 cache identity，确认检查的是这一条消息，不是其他附件。
- B 长按该文件卡片，选择“为我删除”并在确认对话框点击删除。气泡消失；异步清理完成后目标缓存目录不存在，仅保留 .deleted 防复活标记。
- B 强制结束应用后重新启动，进入原私聊，该文件气泡仍不存在，列表摘要回到此前测试文字。没有卸载或清除应用数据。
- A 仍显示文件气泡，发送端对应缓存仍包含 0.block 和 retained。服务端该文件消息只入库一条，隐藏记录一条，senderHidden=0、recipientHidden=1。

原始 UI 转储保存在隔离构建目录 build/media-delete-*，不提交会员信息和设备私有路径。下载目录中的专用源文件是用户选取源，不属于应用缓存，本次没有删除它。

结论：本次普通文件的接收端读取、消息删除、本地加密缓存清除、防复活及对方副本保留通过。未把该证据扩大到图片、视频、语音、同账号多条消息共享资产或整会话清空；这些仍按目标矩阵继续验收。

## 共享源自动化补验

新增私聊/群聊各一项真实 SQLite 与加密文件缓存回归：删除消息立即为独占下载副本留下删除标记；待发送队列引用使共享发送源保留；关闭并重开历史数据库后仍保留；队列移除时，另一会话中收到的同资产消息继续保留源；最后一条引用清空并回收后，源块与 retained 标记消失。与既有语音延迟清理及队列引用互斥测试合计 6 项通过，修改测试文件 analyze 无问题。

首轮新测试缺少历史契约要求的 text 字段，被正常校验拒绝；补齐空文本后通过，未放宽生产校验或修改清理实现。本节是自动化证据，不冒充多条共享文件的双机 UI 验收。

## 图片、视频发送确认窗口清理补验

新增私聊/群聊 × 图片/视频四项 SQLite 与真实磁盘缓存测试：模拟服务端消息已写入历史、发送队列尚未移除的窗口，此时清空记录应删除消息专属副本并建立防复活标记，同时保留发送队列仍引用的源文件。关闭并重新打开历史数据库、执行延迟清理后，源内容仍完整；随后移除队列引用并回收，源文件确实从磁盘消失，重新打开缓存后无法读取已删源。同名但属于另一账号的文件内容保持不变。

这四项与既有共享语音/文件、删除竞争及引用保护合计 16 项测试通过，修改文件 analyze 无问题。测试未发现需要修改生产实现的问题，因此没有为纯测试改动重新打包或覆盖安装。此证据覆盖持久化及发送确认窗口的所有权规则，不是图片/视频编解码质量、真实手机断电或多机会话操作的验收。
