# 多公网候选发现

实际跨网测量显示，同一个手机 UDP socket 面向不同公网观察点时可能得到不同的公网映射。此前客户端在任一 STUN 成功后会停止查询其他观察点，只能向好友通报一个公网候选；这会遗漏运营商 NAT 已经分配出的其他可尝试路径。

本节点保留一个 UDP 数据 socket，并按配置顺序查询最多四个 STUN 观察点。每个观察点独立保存映射及单调时钟时间，30 秒刷新、60 秒失效；相同映射去重。控制消息继续保留旧版 `public` 字段，同时增加最多四项的 `publicCandidates`，旧客户端仍可读取首项，新客户端合并去重后探测全部候选。STUN 结果只提供候选，仍须通过现有端到端加密 challenge/pong 才能成为可用路径。

新增候选不会清除仍然有效的已认证直连；本机网络变化、路径超时或发送失败仍按原逻辑重验并回退到 SuperVM/WSS 与 HTTP。候选挑战的有界容量从九项调整为十二项，对应四个局域网、四个公网、两个 IPv6 和两个已认证反射端点，三秒有效期、单次消费及重放限制不变。

验证覆盖三个真实本机 UDP 观察 socket：客户端依次访问全部观察点，所有请求来自同一个数据端口；两个不同映射均被通报，第三个重复映射被去重，且路由不会仅凭 STUN 进入 ready。静默主观察点、迟到 STUN 响应、IPv6、反射端点、启动打洞、控制通道阻塞隔离及十二项 nonce 容量回归均通过。

这项改动增加可尝试候选，并不等于完整 ICE，也不能保证运营商端点相关 NAT 一定直连。实际 A 移动网络、B 家庭 Wi-Fi 仍须用包含多个真实公网观察点的构建验收；直连失败时必须保持自动中继回退。

## 候选增量更新的连续性修正

复核发现，前述“新增候选保留直连”的实现不完整：虽然被选中的通报地址仍在列表中时会保留 ready，但任何候选列表变化都会递增 endpoint epoch、清除未完成挑战和已认证反射地址。第二个 STUN 结果到达时，可能丢弃仍在加解密的数据、拒绝首个候选的迟到 pong，或撤销实际 NAT 反射地址上的已建立直连。

修正后区分纯新增与撤回/替换：只要所有旧候选仍存在，保留 epoch、未到期的单次挑战、反射地址和已确认通道；新增地址仍需认证探测。任何旧候选撤回/替换仍统一失效并重验，不继续发送已失效地址上的在途数据。本机网络变化、六秒活性窗口、三秒挑战有效期和重放限制保持原状。

新增七项真实本机 UDP / 原生加密通道回归，覆盖候选加入时的旧挑战、通报地址与反射地址双向数据、在途加密发送、在途解密接收，以及候选撤回后的发送终止和反射地址失效。与候选发现、挑战容量、反射端点、打洞启动、控制通道隔离及 IPv6 合计 25 项通过；改动文件静态分析无问题。本项验证的是路径连续性，不代表 A/B 跨网直连已成功。
