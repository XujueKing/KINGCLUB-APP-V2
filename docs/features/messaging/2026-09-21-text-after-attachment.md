# 附件先建立连接后的文字接收

71ebc228 双机公网验证：图片回退完成后，B 发文字 `51aa94c0-66c6-4128-947c-2b65c062987c`，A 界面收到，但 A 的 peer 日志没有该条，B 的 peer delivered=0。因此不能把这条记为 peer 恢复成功。随后 A 发 `5ae23fa2-2356-4751-989e-5aed9b241e05`，两端 peer 日志匹配，A delivered=1。

核对实际路径发现 `MemberRelayText` 只订阅 `incomingChannels`。附件接收方主动打开的共享连接只有 `channels` 事件，文字监听不会建立；对方复用这条连接发文字时，没有文字消费者。直到本端调用 sendText，才补上监听。这与上述实测顺序一致。

改为订阅 runtime 的双向 `channels`，与附件消费者一致；同一 link 的重复事件沿用原消费者。群文件仍通过独立的 groupFileChannels 处理，不混入普通私聊。

新增回归仅发出本地主动创建连接的事件，在本端未调用 sendText 前注入对端有效文字，验证落盘、界面变更事件与 ACK；重复连接事件不产生重复记录。该回归及既有文字持久化、重试/生命周期和自适应冷却共 14 项通过，静态分析通过。此修正尚待双机安装；前述真机结果属于修复前版本。
