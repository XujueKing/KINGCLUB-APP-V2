# 原 A/B 网络的有界多套接字对照

保持 A 移动数据、B 家庭 Wi-Fi，使用独立诊断进程而非业务聊天 socket。
A 开 128 个 UDP socket，从其中四个向固定 STUN 观察公网候选；这次只得到
一个不同的候选公网 IP。协调信息与一次性随机 token 通过主机私有管道交换。

单次实测：

| 角色 | socket 数 | 发出探测数 | token 回复数 | 收到 ping | 收到 pong |
|---|---:|---:|---:|---|---|
| A pool | 128 | 1024 | 0 | 否 | 否 |
| B single | 1 | 1360 | 0 | 否 | 否 |

B 上限 2048 包且最多主动探测 4.5 秒；实际受循环调度影响低于包数上限。
两端观察八秒后关闭所有 socket，临时 dex 已删除。未改网络、路由器、安全组、
安装包，也未发送聊天业务消息。没有自动提高预算或重跑。

JVM 本机正向校验使用同一 Java 程序、私有 IPv4 地址与 loopback STUN stub，
pool/single 两端均 ping=true、pong=true，确认基础收发与 token 回复逻辑。
它不验证 Android/运营商网络上的所有行为。

本次没有打通，不能将此方法直接接入后标为解决。已知 A 面向不同目标可能
改变公网 IP，四个面向固定 STUN 的观测不保证覆盖面向 B 的 IP；候选不覆盖、
过滤、随机探测未命中等都仍可能解释负结果。不能宣称任意策略都不可能成功。

此为 reachability 对照，不是生产加密协议；共享随机标记明文发送，无业务
数据。生产路径若采用多 socket，仍必须保留原生身份鉴权、AEAD、一次性
端点挑战及媒体回执，并单独验证路由选择、退出清理和恢复。

## 两个观察点的后续对照

使用自有 STUN 与此前已使用的 `stun.cloudflare.com:3478`，A 的前四个
socket 分别查询两个观察点，共八个映射样本，得到两个不同的公网 IP。
只向 STUN 服务发送地址发现请求，不发送聊天内容或密钥。

保持原总包数/时长预算，B 在这两个候选 IP 之间分配随机探测：

| 角色 | socket 数 | 发出探测数 | 回复数 | ping | pong |
|---|---:|---:|---:|---|---|
| A pool | 128 | 1024 | 0 | false | false |
| B single | 1 | 1305 | 0 | false | false |

此次仍失败。两个 STUN 观察到的 IP 不保证包括 A 面向 B 的真实出口，且
固定总预算分摊到更多候选降低每个 IP 的命中机会。因此不能据此证明网络
绝对无法直连，也不能把“候选数量增加”当作功能完成。

本地两观察点正向校验通过：pool 返回八个映射样本，两角色均收到 ping/pong。
临时手机 dex 已删除，网络及聊天安装包不变，未自动扩大探测预算。
