# NovoRUDP 附件接收协调

源码核对：NovoRudpFileSender/Receiver 尚无聊天产品调用方；ChatFileDownloader 仍通过服务端分块授权下载。MemberRelayText 只承载文字，不将独立 UDP 测试计为附件双通道交付。

下一步协调层持有已认证 FrameLink 和由调用方独立授权的文件大小/摘要及传输 ID，过滤其他消息流，接入 Receiver 的落盘和 ACK，完成后才返回摘要验证文件。每次处理前后检查当前访问授权；超时、断线、权限撤销必须失败并清理临时文件，不关闭同通道其他聊天。成功文件由协调层持有至调用方复制并关闭。

这一层不从对端自行授予权限、不创建聊天消息、不把 ACK 当作服务端入库；授权消息与设备的协商、聊天下载调用和实际双机自动切换仍待接入。验证先用真实原生加密 UDP 与磁盘，不能代替手机验收。

已实现 NovoRudpFileDownload：使用调用方授权判断，过滤不匹配流/对象和非数据帧，接收任务最多256个，完成前校验大小与摘要，超时/会话变化/失败清理；关闭仅释放该文件，不关闭共享链路。成功结果供调用方复制后关闭，仍未接入产品下载器。

验证：Windows 真实原生 DLL + 加密 UDP + 临时磁盘，协调层4项通过（70KB完整性、其他流隔离、摘要错误清理、超时、撤销授权及关闭后共享链路继续可发）；发送器/接收器原有回归及首批协调层共17项通过，随后新增摘要用例并重跑协调层4项。18MiB丢包用例耗时70780ms，25484包中主动丢3595包，校验一致；这是受控回环故障测试，不是手机或公网速度指标。两文件 analyze 通过。日志保存在 build/peer-file-coordinator-*.log，未安装手机。下一步仍需消息授权协商、运行时接线与服务端下载回退。

聊天下载接入阶段：给 ChatFileDownloader 增加显式授权 peerDownload 提供方，仅单聊尝试，接入前保留服务端 grant 校验，文件复制到下载器自己的临时目录后独立校验大小/摘要，再复核权限。失败先关闭直连接收，重新授权后按原 HTTP 下载；取消/换号不回退。连接最多3秒，迟到连接必须关闭。运行时尚未提供该连接器，因此默认路径仍是服务端，不宣称产品已启用直连。

验证：聊天下载器接真实原生加密 UDP 接收层，两项通过（独立复制后校验正确且零HTTP二进制请求；传完后的最终授权撤销拒绝交付并清理）。授权接口为受控响应，不代表真实服务端协商。现有HTTP下载及新增直连不可用回退、连接中取消共23项通过；取消在500ms内终止且不发HTTP，迟到连接清理。三文件静态分析通过。运行时 peerDownload 仍未提供，产品默认路径未切换，下一节点须接可信会员/消息协商后才能双机验收。

初始化清理补充：接收临时文件创建后的第二次权限检查，无论返回拒绝还是抛出异常，都关闭接收器并删除其临时目录，再向调用方传播失败。新增两项真实原生链路初始化测试，确认零发送、源文件保留、接收目录清空；协调层共6项通过，两文件静态分析通过。尚未启用产品直传，不为此单独重装手机。

接线核对：现有 direct-file-media 授权只返回调用者自身的下载凭证，不能当作对另一会员的发送许可；必须独立核对请求者与消息的关系。chat_file_send_page 在发送完成后删除草稿，因此当前也不能假定发送端持续持有源文件。后续运行时接线需要同时解决受权消息协商和有界源文件保留，不能仅把可选 peerDownload 设置为非空就宣称附件双通道完成。

发送源保留设计：复用现有 AES-GCM 分块缓存，使用独立 sent-file 用途和会员密钥隔离；只保留已持久排队的文件副本，单文件不超过64MiB、最多4份、24小时过期。大文件或缓存故障仍保留正常服务端发送结果，不向用户误报发送失败。读取需调用方提供当前会话检查，逐块解密并校验完整摘要后才交给受权发送回调，临时明文在回调结束时删除。缓存内容不构成消息权限，运行时发送前仍须独立校验消息双方与当前授权。发送页在删除草稿前尝试保留；未接通消息协商前不会因缓存存在自动发送给任何设备。

发送源保留已接入文件发送页（排队后、删除草稿前），未接收远端请求或启用自动直传。ChatSentFileCache 复用加密块缓存，独立会员/用途目录与密钥，串行维护最多4份，逐块校验会话，失败清除不完整副本；完整解密副本只在回调期间存在，结束或报错删除。超过64MiB直接跳过缓存，继续原服务端能力。验证：新增保留缓存7项与上传续传10项共17项通过；先前下载缓存2项与草稿恢复6项通过；5文件静态分析通过。测试覆盖空文件、多块文件、草稿删除后的完整读取、损坏/过期拒绝、账号变更、发送回调失败、上限淘汰和上传器缓存故障不重复发送。真实手机尚未安装此节点，源文件保留不等于消息授权协商完成。

消息授权接口契约：MessagingRepository.peerFileAuthority 调用新686接口（messageId、peer），服务返回真实双方和摘要及15秒 expiresAt；目前仅调用入口，未在下载器/中继运行时启用。服务118迁移和授权逻辑已完成本地完整verify，尚未部署或真实数据库验收。App该文件静态分析通过，手机默认HTTP路径不变。接线时必须核对结果双方与已认证设备通道、比较消息清单，传输开始和交付时重验，不信任对端发送的授权结果。

设备协商协议：已认证会员通道内使用独立控制流KCFC与数据流KCFD，每次请求随机64位对象号，仅发送消息编号和请求号，不接收对端自报文件路径或可信清单。收发双方各自调用686，严格验证返回身份/文件清单/有效期；发送方仅从当前账号加密缓存取文件。request/ready/reject控制消息支持请求重试，单通道同时最多一发一收，拒绝无界排队。权限短租约在传输期间刷新，失败终止；关闭仅清理本协议任务，不关闭共享聊天链路。协议实现后仍需接MemberRelayRuntime和下载器并完成双机验证。

协商层已实现 PeerFileChannel：独立控制/数据流，一发一收上限，请求重试及ready/reject，双方独立686授权与严格清单解析，受限加密源缓存供给，5秒权限刷新，逐帧发送/接收检查有效期，取消不关闭共享链路。控制发送最多等待1秒，请求接受最多3秒。新增 PeerFileAuthority 验证方向、消息、资产、大小、摘要和短有效期；协议对端不能提供可信路径或替代服务授权。

验证：真实原生DLL/加密UDP的完整协商、缓存缺失、发送端身份不符3项通过（授权HTTP为受控响应）；授权解析13项通过；发送器与接收协调全文件21项通过，包含18MiB丢包修复与取消/会话变化/超时，逐帧权限拒绝新增用例零发送；5文件静态分析通过。控制超时修改后重跑协商3项通过。5秒刷新分支尚未进行双机长传验收。MemberRelayRuntime/产品下载器尚未创建此协商通道，自动直传仍未在手机启用；下一节点接运行时和真实686接口发布，不把独立协议测试计为产品交付。

运行时接线设计：MemberRelayFiles与文字协议共同监听已认证通道，各自只处理自己的流，不占用/关闭共享链路。文件卡片携带原消息sender作为寻址线索，686再次核验为真实发送方；本人发送或群文件跳过对端下载。NovoRudpBindingRuntime建立文件消费者并给ChatFileDownloader提供受当前会话约束的连接函数；中继不可用、目录无在线设备、授权接口失败或缓存缺失返回原HTTP路径。采用KINGCLUB_NOVORUDP_FILE_TRANSFER构建开关，在686发布与双机验收前默认关闭，避免未部署接口引入等待。

运行时接线已实现：MemberRelayFiles在NovoRudpBindingRuntime中创建，与文字通道共用认证链路；新增runtime.channels同时通知主动和被动建立的连接，避免文字主动连接建立后附件请求无人处理。最多维护8个文件通道，切后台、断开或换号关闭文件任务；文件缓存初始化失败不影响文字。文件卡片及历史上下文传递真实sender线索，686独立复核，下载器最终交付前再次复核对端授权。本人发送及群文件不尝试对端来源。开关默认关闭，686未上线前不启用。

验证：启动本机现有SUPERVM测试中继（确认无监听后由受控脚本启动），Windows原生DLL+真实TLS中继完成两种文字路由模式下4097字节附件传输，复用原先由文字主动建立的连接；随后文字/已读/前后台重连原用例均通过。设备目录和686响应为受控测试契约，不算真实会员双机验收。HTTP下载及详情24项通过；原生UDP下载最终普通权限与对端权限撤销3项通过，均不交付；8文件静态分析通过。此节点未重新安装手机，下一步最小发布686并开启测试构建。
