# 2026-09-11 照片核验压缩与存储增量方案

用户要求：姓名/身份证/人脸核验接入新服务器；避免高分辨率手机照片过大，自动压缩同时保证可识别人脸清晰度，并明确数据库保存方式。本文件是接入设计和待验收要求，不表示真实接口已完成。

## 已核实状态

真实实名页仍提示服务不可用；CCSOP只有MockIdentityAdapter，尚未完成腾讯真实照片adapter、申请照片及核验结果闭环。已完成的短信登录/会员分流不能算作实名完成。公共platform_file_object及LocalStorageAdapter可作为存储底座，尚未专门接入实名照片。

旧registration-photo.js使用multipart上传文件并拿token，不是全程Base64上传。旧RegistrationPhotoProcessor已实现EXIF方向、缩放、MozJPEG、大小控制和临时token；但先上传原图，15MiB限制和网络耗时仍可能阻断高像素照片。旧Java兼容路径有重复Base64编解码，不宜直接复制。旧快照不等于当前线上版本证明。

## 新处理流程（实施参数，需样片验证）

1. 手机端拍照后先按目标像素采样解码，避免高像素原图完整解码造成内存峰值；纠正方向、去除GPS等元数据，转换JPEG。已有小且清晰的JPEG尽量不重复有损编码。
2. 初始建议长边1600px、JPEG质量85附近，目标约300KB～1MB；复杂画面允许适当更大。通过实际编码字节数迭代质量/尺寸，每轮从原输入或同一解码图生成，不能串联压损。核验上传JPEG上限暂定2MB，并独立核对Base64长度。上述为项目建议，非腾讯官方清晰度保证。
3. 图片达标与脸部达标分开：检查单人脸、有效脸部像素、清晰度/遮挡/光照；过度缩小会使脸部失真，达不到质量门槛应提示重拍。缩放/编码保留五官原貌，不把美颜或生成增强作为核验输入。最终质量门槛用不同手机真实受控样片测定。
4. App通过HTTPS multipart二进制上传受控私有接口，获取绑定actor、用途selfie、申请版本和有效期的fileId/token；姓名/身份证通过加密业务接口单独提交。服务器检查实际格式、字节、像素、所有权和用途；不信任扩展名或客户端自报压缩结果。上传进度/失败重试与核验调用分离，重新上传不自动重复收费。
5. 服务端仅在调用腾讯所需时将达标JPEG转标准Base64，不将Base64写日志/数据库。核验请求以申请+照片版本+幂等键防重，保存RequestId、状态、必要结果和版本。超时标记结果未知，不能自动重复收费或假成功。

## 保存模型

- 图片字节：当前先使用服务器私有持久文件存储，存储适配层后续可切对象存储；无公开人脸URL，访问需鉴权或短期签名。核身自拍与公开头像/形象照片分用途管理。
- platform_file_object复用：fileId、actor、storageKey、格式、size、SHA256、私有属性；尺寸、压缩策略版本等补入受控元数据。原文件名不采用手机号/姓名/身份证，统一随机命名。
- 核验/申请表：保存fileId引用、步骤/状态、供应商RequestId、接口/策略/照片版本、必要结果及时间。不存图片BLOB/Base64或完整腾讯响应。
- 姓名/身份证：归统一身份权威域；需要留存时使用字段加密与独立密钥管理，检索/去重用带密钥HMAC，App只拿必要脱敏摘要。KingClub不复制一套明文证件资料。
- 临时失败/废弃文件自动过期清理；正式核验照片与必要凭据保留期需按业务要求单独确定，不默认永久保留高清原图。不能清理仍被进行中申请引用的照片。
- 后续具体表/接口采用递增migration同步公共目录；依database_review.md逐功能核对事务、副作用、重传版本、对账及回滚，本批未建新表或改变旧数据库。
