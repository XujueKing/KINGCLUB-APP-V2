# 美团、抖音团购券：存入储物袋与订单直接核销

状态：In Review。用户明确两种入口都要支持，且必须接入美团、抖音官方核销 API；本轮继续先文档，不以模拟核销代替真实接入，也不执行真实核销。

## 1. 两种入口，一份外部核销事实

| 模式 | 会员操作 | 核销成功后的本地结果 |
|---|---|---|
| 存入储物袋 | APP 扫外部团购码，展示店、券种/套餐、份数和期限，确认兑换 | 生成关联外部核销流水的 APP 券，放进储物袋，可按适用范围参与卡座局/兑换 |
| 订单直接使用 | 点单付款页选择美团/抖音团购券，扫描并确认本订单要用的份数 | 直接登记本订单的券支付/权益履约，不要求先存袋，不生成额外可用券 |

两种模式共用同一个外部券消费记录和防重约束。一张券或一次可核销份额只能形成一个本地用途；扫码字符串可能刷新，不能以二维码文本作为唯一消费身份。使用平台、授权商户、外部订单/券及核销份额/序号等经渠道确认的稳定标识。

APP 券是本地业务权益，不是再发一张美团/抖音原券。储物袋可统一展示“酒 / 物品 / 券”，底层会员保管实物与可消费权益分开。不得把现有通用物品减数量的核销直接当成完整券支付。

## 2. 存券流程

扫码识别渠道 → 服务端使用该商户授权准备验券/查询 → 返回可用券列表 → 会员选所需份数并确认对应 APP 权益 → 核销 → 持久化渠道结果 → 幂等发放 APP 券 → 储物袋刷新。

APP 券保留发行主体、适用店/品牌、套餐版本、有效期、剩余次数/数量、外部来源和状态。不能按外部券面额随意变成通用现金余额，不能自动延长原权益期限；本地承诺期限及可延期范围需按已确认商品规则设置。一个码包含多券时只核销会员选中的券，不能自动把整单都核完。

这里的“存券”是用户要求的业务模式；具体券种能否在未消费时先核销换成本地权益，要按适用行业、商品约定及平台授权确认。未获适用确认的券种不能偷偷先核销，可保留待办理申请并提示到店/消费时使用；不将存券成功与仅保存码图混为一谈。

## 3. 订单直接用券

先锁定订单报价、门店和券可覆盖的商品/份额 → 校验名额或库存 → 用户确认核销 → 渠道成功后登记该订单的支付组成 → 满足整单支付/成团条件才进入对应履约。

- 套餐券按映射套餐核验，不默认当任意金额代金券；代金券按明确适用商品、门槛、抵扣上限计算。
- 订单包含非券覆盖内容时，明确还需支付多少；是否允许混付、部分核销、找零及多券叠加按产品规则配置，不能默认兑现金找零。
- 如果是 AA 入局，核销成功形成绑定本次入局的权益，不再多发可重复入局的袋内券。
- 如果允许券参与加餐 AA，它只覆盖当前会员依法定商品规则可支付的份额，不能代替其他参与者付齐；本期是否开放此种券的 AA 加餐适用范围仍需确认。
- 基础套餐仍在员工确认开局备酒时整桌出库；直接买单付齐出库；加餐 AA 人数及款项齐后出库。外部券核销本身不能重复扣共享套餐。

同一订单等待补差时保留已核销的资金/权益事实和履约预留。补差失败不能把已核销券当作“未使用”直接释放给另一订单；进入可追踪的取消/恢复流程。

## 4. 一致性与异常处理

概念记录：ExternalVoucherIntent（存袋/订单用途）、ExternalVerification（渠道事实）、AppCouponGrant（本地发券）、OrderVoucherTender（订单支付组成）、VoucherRecoveryTask（补偿任务）。最终表和接口编号待审，不新增迁移。

意图状态建议：待确认 → 核销中 → 外部结果待查 / 外部核销成功 → 本地处理完成；明确失败和撤销处理中单独记录。渠道成功与本地完成是两个事实。

- 调外部平台前持久化请求身份、用途、商户/门店和绑定对象；不在数据库长事务里等待外部接口。
- 渠道已成功但本地事务失败：凭原核销结果补记，只发券或入账一次，不再次核销，不显示“券丢了”。会员查看“处理中”，最终结果可追踪。
- 超时/网络断开：查原核销结果、使用渠道支持的幂等重试；不能凭超时判失败、换身份重扫。
- 同券分别从两个入口或两台设备扫描：只有一个意图获得处置权。提示原用途/办理状态，不向另一个会员泄露原持有人隐私。
- 直接订单失败或取消：在渠道支持的范围内申请撤销核销/退款；撤销、退款、恢复 APP 权益是不同操作，不能假定总能原路自动恢复。
- 如退款或平台撤销涉及已发 APP 券，先检查本地是否已用、锁定关联权益；不得既退外部款又留下可消费券。已消费进入关联售后，不静默清账。
- 待恢复任务、员工处理记录和用户回执按门店授权；保留操作者、会员发起人和渠道商户三个身份。

## 5. 官方 API 接入清单

CCSOP 内分别建设 DouyinVoucherAdapter、MeituanVoucherAdapter，统一内部能力为授权状态/门店映射、准备查询、核销、结果查询、撤销核销及对账。具体渠道不支持的能力明确返回不支持，不能用本地改状态伪造。App 不持有商户密钥；扫码数据只发业务后端，日志和分析平台不记录原始券码或访问令牌。

平台应用资质、商家授权、渠道商户/门店与本地经营主体/门店映射是经营功能真实接入的前提。后续开店/代运营后台可以延期，但这些必要配置和授权不能一并延期；先提供受控的最小配置流程，不能全平台共用一个老板的核销账号。

### 官方资料核对（2026-09-17）

- 抖音生活服务的 [团购核销能力](https://developer.open-douyin.com/docs/resource/zh-CN/local-life/develop/capability/basic/verify-introduce) 说明需完成应用接入和相应能力申请。
- [验券准备](https://developer.open-douyin.com/docs/resource/zh-CN/local-life/develop/OpenAPI/general-capabilities/life.capacity.fulfilment/certificate.prepare) 用于取得抖音码对应可用券和加密券码；二维码可为短链，不能固定长度截取。
- [验券接口](https://developer.open-douyin.com/docs/resource/zh-CN/local-life/develop/OpenAPI/general-capabilities/life.capacity.fulfilment/certificate.verify) 为 POST https://open.douyin.com/goodlife/v1/fulfilment/certificate/verify/，要求接口权限和商家授权；使用 verify_token、poi_id 等渠道参数。需按完整业务返回判断结果，不能只看 HTTP 200。
- 美团 [技术服务合作中心](https://developer.meituan.com/) 为官方入口，本轮公开页面未返回可审读的团购接口契约。具体鉴权、查询/核销/撤销路径、签名与回调字段须在授权官方文档中核实，尚未冻结端点，未采用第三方聚合核销服务或非官方 SDK 作为依据。
- 美团 [商户履约规则](https://rules-center.meituan.com/v1/mss_7482cc6672ce4e76a32d7d7c3161ac24/rules-center/c7d16d50-2104-4bb5-9073-558b554b4321-53229755/%E5%88%B0%E5%BA%97%E7%BB%BC%E5%90%88%E4%B8%9A%E5%8A%A1%E5%95%86%E6%88%B7%E5%B1%A5%E7%BA%A6%E4%BF%9D%E9%9A%9C%E7%AE%A1%E7%90%86%E5%8A%9E%E6%B3%95.pdf?openInApp=2) 涉及未实际履约前核销限制；具体行业现行规则与“换本地券”模式的适用性需按实际商户确认，不能从 API 可调用推断任意提前兑换都已被允许。

以上仅文档查阅；未申请账号、读取密钥、连接商户后台或调用真实验券接口。服务商身份、商户授权和具体券商品映射是接入前待补项。

## 6. 验收（未执行）

存袋与订单两入口分别成功；一张券跨入口并发不双花；一批多券仅核选中份数；核销成功本地失败可恢复；迟到结果和刷新码不重复发券；错店/错商品/无授权不核销；补差失败及撤销有闭环；储物袋券使用一次后不可再用；AA 未付齐不出库；外部款待结算与 APP 现金收入不重复计算；四语言展示保持同一券、金额和归属。所有业务测试使用渠道许可测试券和合成数据，不能用真实客户券试错。
