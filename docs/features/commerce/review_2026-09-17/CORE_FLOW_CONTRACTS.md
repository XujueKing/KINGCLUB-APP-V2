# 核心页面、接口与状态契约草案

> 最新已确认规则见 [营业规则确认](CONFIRMED_OPERATING_RULES.md)：活动不限报名人数、开局前分配卡座，按各卡座最小/最大人数开台；加餐 AA 有效 30 分钟，未付齐退 APP 余额；AA 门票酒禁存，单点/购买套餐由购买者存酒、仅原店取、保管 3 个月；券按配置选择使用，成本按进货价；收银硬件第二期。本文较早的冲突描述以该确认为准，技术方案仍待评审。


状态：In Review，未批准编码。用户确认目前尚无抖音平台账户，先推进内部设计；第三方官方接入保留为必做项，账号和权限未就绪时不执行核销。本文件使用语义用例名，不占用正式 K 接口编号。

## 1. 通用约定

每个写请求携带 requestId 和目标对象版本，业务数据另列。服务端从会话取得实际操作人，验证经营主体、门店和对象归属；客户端可选门店但不能自报权限。金额传精确最小单位及币种，数量传明确单位，ID 不以浮点保存。

响应统一包含业务对象 ID、状态、版本、可执行动作及结构化错误码；外部请求未知返回 processing/unknown，不谎报失败或成功。重复请求内容相同复用结果，内容不同拒绝。客户端超时后查原单，不自动创建第二单。

用户界面按简体中文、英文、繁体中文、泰语渲染同一状态；切语言不改店、金额或请求身份。关键确认页必须显示门店名称、业务日期和操作内容。

## 2. 地区、门店、活动报名与卡座分配

会员选择地区/门店/活动报名，显示活动套餐、日期、报名条件、本人待分配/已分配状态；无活动报名人数上限，不以单桌容量限制报名。员工查看报名池与各卡座最小/最大人数、配比、已分配和已入座人数。

语义用例：ListStoreActivities、JoinActivity、PreviewSeatAllocation、ConfirmSeatAllocation、AssignSeatManually、InvalidateUnassignedRegistration、RequestTicketReturn、ConfirmSeating。报名传活动及权益引用；分座传报名引用、卡座本次开台引用和版本。身份/权限由服务端验证。

报名事务检查门店、活动、权益与重复报名；分座事务检查卡座容量、配比及重复占位。达到卡座最小人数可由员工确认开台，不能超过最大人数。自动方案可调整，提交与人工分座共用约束。未分座人工决定失效及退票，失败退票显示待处理，不误报到账。

待细化：改局/换桌权限、退票资金或权益去向、套餐内容配置。最低开台人数已由卡座初始化配置决定，不再列为待定。

## 3. 点单及付款方式

**入口**：当前门店/卡座局 → 商品 → 购物车 → 「直接买单 / 发起 AA」。两项同级可见，不藏在备注里。

**显示**：商品和套餐内容、数量、缺货、优惠、应付、履约位置。若为 AA，增加参与人数、每份金额、截止规则。库存只展示当前门店可售量。

**用例**：QuoteCart、CreateDirectOrder、CreateAAGroup。提交商品 ID/数量、局或桌台引用、支付方式；价格、优惠、套餐配料与份额由服务端生成快照。

**直接买单**：报价 → 原子预留 → 付款中 → 已付并销售出库 → 待备/待送 → 已交付。现金由有权员工确认实收，走相同订单与库存确认入口。

**券直接付款**：GetVoucherPreview → ConfirmVoucherForOrder → 查询原请求结果。先显示券覆盖内容及补差，不把套餐券自动当现金。外部核销成功后只登记该单支付，不生成额外可用袋内券。

**异常**：价格/库存变化需重新确认；支付未知保留原单；无渠道配置不能进入真实收款或核销。上桌确认不二次扣库存。

## 4. 加餐 AA

**显示**：发起会员、商品明细、总人数、每份金额、已付人数、截止时间和当前状态；会员本人可见自己的付款/退款进度。

**用例**：CreateAAGroup、JoinAndPayAA、GetAAGroup、CloseExpiredAAGroup、GetParticipantRefund。一个人即可发起，页面以“共 N 份、已付 X 份”显示；发起不算已支付。创建成功后 30 分钟到期。

**状态**：collecting → forming → formed；未成团关闭进入 closing → refunding → closed。形成中不提前展示点单成功；部分退款失败时保留 refunding 和待处理明细。

**规则**：整份加餐库存一次预留；个人付款成功增加有效已付份额；最后一份付款确认时锁定团与对应库存/订单，验证人数、总金额和有效预留后唯一成单、出库。异步外部付款不能用一个数据库事务“全部回滚”。

**竞态**：超时关闭与最后付款共用状态判定；关闭后迟到付款进入可追踪退款，不复活已取消团。余额支付等内部变动按独立幂等流水处理。失败退款不能假装完成。

**已确认**：自行找人 AA，30 分钟内全部付完成单，未付齐系统自动将实付金额退回各付款会员 APP 余额，按原付款流水去重。

**待细化**：代付多份、提前取消、邀请交互及券配置是否允许付 AA 份额。

## 5. 储物袋券与第三方兑换

**显示**：酒/物/券分组；券卡显示发行方、可用门店、套餐/抵扣规则、数量/次数和期限。不能仅显示券面额让人误以为可到处消费。

**用例**：PrepareExternalVoucher、ConfirmVoucherToBag、GetVoucherIntent、ListAppCoupons、ReserveAppCoupon、ConsumeAppCoupon。模式 toBag/toOrder 在服务端确认前固定，不能途中切换造成双发。

**状态**：prepared → verifying → verified_pending_local → completed；不确定为 unknown，明确失败为 failed。completed 的效果为“发券”或“订单券支付”二选一。

**首阶段自动渠道未接通**：不向外部平台发起自动核销，不接受顾客扫码即成功；已有合法本地券仍可按规则使用。员工官方端核销后的人工确认作为过渡提案，详见 [分阶段方案](EXTERNAL_VOUCHERS.md)，记录人工来源而不是 API 成功。文档/原型的合成样例不标成真实成功。

**待定**：每个外部商品与 APP 券的映射、可提前兑换的适用范围、补差/叠加规则、撤销后权益处理。正式 API 接入按官方业务授权执行。

## 6. 员工开局与整桌备酒

**入口**：手机/吧台桌台详情 → 开局备酒。

**显示**：门店、场次、已预定/已入座会员、开局条件、共享套餐完整内容、待出数量和缺货。每桌有一个唯一共享套餐履约单。

**用例**：PreviewSessionOpening、ConfirmSessionOpening、ConfirmTableDelivery。员工确认开局并准备酒水时，在同一事务内检查权限与配置、转换整桌预留为批次出库并建立备酒/交付记录。重复确认返回原单。

**分次上桌**：记录已送/待送数量，只影响交付状态；不能重复扣同一份套餐。临时加酒、赠送或损耗使用另外的有原因单据，不篡改套餐已出明细。

**异常**：缺货或批次不可用不显示备酒成功；配置变化先提示差异；取消已出套餐时按实物可回库数量处理，不凭退款自动补库存。

## 7. 存酒、取酒与核销

**存入**：创建申请 → 会员出示存酒码 → 员工扫码核实实物/数量/余量/期限/归属 → 确认保管 → 双方回执。扫码查看不增加数量。

**取出**：会员选具体记录与本次取用量 → 出码 → 本店员工核对 → 确认交付及核销 → 余量刷新。码绑定用途/申请版本，重复扫码不能重复取酒。

**用例**：CreateWineDepositRequest、ConfirmWineDeposit、CreateWinePickupRequest、IssueCustodyCode、PreviewCustodyCode、ConfirmWinePickup、GetCustodyOperation。沿用现有储物服务基础扩展，不直接对外开放主机受信脚本。

**数量约定**：新用户操作填“本次取出”，旧实现参数是“取后剩余”，两者由明确适配转换并校验，绝不能混填。保管数量变动不计销售出库，不进入可售库存。

**已确认**：AA 门票酒禁止存；单点/购买套餐仅购买会员可存，保管 3 个月，不能跨店取。按来源明细校验资格和余量；部分瓶计量和到期处置待细化。

## 8. 采购、收货、日盘点与交班

| 页面 | 输入与动作 | 服务端效果 | 异常重点 |
|---|---|---|---|
| 采购 | 从授权清单选供应商和商品，填计划数量/授权单价 | 建采购单，不增加可售库存 | 禁止自由新建供应商/酒款；错店 ID 拒绝 |
| 分批收货 | 选择采购明细、本次实收、批次/期限，确认 | 本次批次入库一次，未到数量保留 | 重试去重、超收按权限处理，不重复记采购付款 |
| 调酒/耗品 | 选用途、酒款或耗品、实际用量、来源 | 有来源的用量/领用事件 | 已由订单扣减部分只记实际差异，不能双扣 |
| 日盘点 | 可售与保管分开，填实点并核对差异 | 基于计数时点和期间变化形成调整 | 不能覆盖盘点期间销售；差异留原因/操作者 |
| 备用金/交班 | 领用/归还、实点、差额和交接 | 资金调拨及班次结余，关联实际支出 | 调拨不当费用，差额不修改订单抹平 |

语义用例：CreatePurchase、ReceivePurchaseBatch、RecordBarUsage、RecordConsumableIssue、SubmitStocktake、ConfirmStocktakeAdjustment、TransferPettyCash、CloseShift。更正均引用原单与原因；正式字段、批准权限、计量与成本政策待逐页评审。

## 9. 本轮交付边界

这些契约用于让用户评审可操作流程和关键副作用，并非实现或测试结果。三层账、配送/自提、链上商店保留原需求，后续继续补其逐页契约；不因先细化常用流程而删减范围。多语言资源、打印设备和第三方账号实际能力尚未验收，旧数据库仍不导入。
