## 1. 给非专业人员的操作验收

| 场景 | 成功判定 |
|---|---|
| 新进一批货 | 不懂“库存事务”的员工能选商品、数量、单价并确认入库；系统自动创建批次，库存增加且进货付款不重复计费用 |
| 分两次到货 | 同一采购先收一部分、后收余量，分别有批次及实际数量；未到货数量不显示可售 |
| 顾客扫码 | 不用登录经营端或选择仓库，看到正确门店/桌台、可售商品和缺货标记 |
| 点单付款 | 提交时库存被预留；付款成功自动出库，员工只处理上菜/交付，不再手工录一张出库单 |
| 店员现金收银 | 选商品、输入实收、看到找零并确认，订单、库存和现金账关联完成 |
| 每日盘点 | 只填实点数，系统展示预留/待交付影响和差异；确认后产生可追溯调整，不直接改历史库存 |
| 记电费/房租 | 只选分类、填金额/账户、可附照片；后台凭证自动形成，无需输入借贷科目 |
| 看利润 | 能分辨销售、已售成本、费用、未售库存和现金收支；点击利润可追到来源，不需要会计知识才能理解基础数字 |
| 自提/配送 | 顾客只填该模式必要信息，店员看到待交付列表；取货码只完成一次 |
| 链上购买 | 展示买什么、给谁、支付多少及费用；用户明确签名，状态由核验结果决定，不需要店员手动填链参数 |
| 会计查看 | 有权限者可查凭证、明细账、总账、试算平衡和三张报表，日常员工不必进入 |

界面可用性目标：每个日常主操作只有一个明确完成按钮；默认值可解释，必填项仅与当前任务相关。优先使用清单、数字键盘、扫码和原单操作。具体步骤数/视觉尺度通过后续原型观察确认，不凭文档宣布“易用性已通过”。

## 2. 核心合成业务用例

| ID | 输入 / 故障 | 必须满足 |
|---|---|---|
| T01 | 商品库存 1，两个顾客同时提交各 1 | 只能一个预留成功；另一个明确缺货；库存/预留不为负 |
| T02 | 套餐含 A×2、B×1，A 够而 B 不足 | 整份套餐预留失败，A 不残留占用；单品与套餐同时购买也遵守同一库存 |
| T03 | 同一付款成功回调重复/并发十次 | 一次出库、一次收款/资产变更、一套适用凭证；重复查询返回同一业务结果 |
| T04 | 支付确认超时、顾客重开 App | 恢复原支付尝试和订单；不再发起一次扣款，不假显示失败/成功 |
| T05 | 超时关闭与支付成功同时发生 | 锁和状态机判定唯一结果；不能一边释放一边扣减；必要时进入真实已收款异常处置 |
| T06 | 同一采购收货命令重发 | 不重复增加批次库存；修改数量须用新版本/更正动作 |
| T07 | 两批货成本不同，自动销售出库 | 按批准批次规则分配，保存实际成本；后改售价/进货价不改变已完成销售成本 |
| T08 | 顾客付款后等待上菜，员工盘点 | 已售待交付不重复销售；盘点不把待交付当盘盈；上菜不二次扣库存 |
| T09 | 盘点期间发生销售/入库 | 按计数时点和期间变动处理，冲突项重数；不覆盖最新库存 |
| T10 | 部分退款、商品未退回或已损坏 | 原路退款组成不超限，库存仅对确认可再售数量回库，损耗独立记录 |
| T11 | 跨店/跨账号/失权员工操作 | 拒绝下单归属篡改、读取成本/账务、退款和盘点调整；隐藏按钮不能代替校验 |
| T12 | 现金交班应有与实点不同 | 留差额、原因、操作人和归属班次，不自动改销售订单来抹平差额 |
| T13 | 10 瓶成本 30，售出交付 2 瓶售价 50，费用 10 | 已售成本 60，毛利 40，经营利润 30，未售库存成本 240；全额进货付款下现金净流量 −210 |
| T14 | 会员充值后再消费 | 充值不重复算商品销售收入；资产余额与资金、销售凭证各有正确来源关系 |
| T15 | 凭证借贷不平、已锁期间写入、重复事件 | 拒绝错误过账；已记账改错通过关联冲正；不能悄悄修改历史 |
| T16 | 自提码重复使用、错误门店、已取消订单 | 不再次交付；错误请求不消耗其他人的有效取货码 |
| T17 | 配送订单付款后部分发货、退货 | 库存出库/待交付/确认成本和退款分别可追踪，不能一键全部完成掩盖部分履约 |
| T18 | 链上错误网络/资产/收款人/数量的 txHash | 即使交易本身成功也不能匹配商业订单完成交割 |
| T19 | 链交易重复提交、节点断连、签名拒绝 | 明确 pending/unknown/rejected，重试复用意图身份；不替用户签名、不凭传输 ACK 交付 |
| T20 | 已提交链交易达到/未达最终确认标准 | 只有满足冻结的证据和权属条件才成交；回执冲突进入复核且不自动二次交割 |
| T21 | 后台进程在记账/出库中崩溃 | 单库事务无半完成，外部待办恢复后不重复产生业务效果 |
| T22 | 成本缺失、期初/分类未配置 | 展示待补齐/预计，不用零成本伪造利润或正式财务报表 |

这些用例使用人工构造数据。**禁止为测试导入用户的旧数据库数据**；本轮也没有执行这些业务用例。

## 3. 本轮实际检查

- Git/worktree/路径只读核查，写入范围仅 commerce 工作区。
- 旧 SQL 结构与目录的流式扫描，文件指纹与既有盘点一致。
- K_ 导出记录独立解析统计，列数量按结构校验，33,997 行、0 解析错误；与原结构扫描的 K_ INSERT 数量总计交叉核对。该快照每个已识别 K_ INSERT 对应一行，不能把此规则泛化到其他导出格式。
- 对商品下单/回调/上菜的 schema 限定表名和相关触发器补查，避免只按词法短名漏表。
- 文档链接、需求追踪、工作区差异和敏感数据输出范围检查。

没有执行真实数据库/支付/退款/出库、VM 节点、手机操作、App 编译或业务测试。文档提交与推送不代表新架构通过验收。
