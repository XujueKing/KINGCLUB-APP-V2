# 简单经营工具的架构提案

状态：In Review。本轮不实施，不导入旧数据。用户允许五模块重新设计；保留 Flutter/CCSOP 的成熟底座，不重做聊天、登录或 VM 内核。

## 1. 总体分工

```text
KINGCLUB Flutter
  顾客：商店 / 扫码点单 / 我的订单
  员工：经营首页 -> 收银 / 库存 / 记账 / 商品
                    |
             现有会话与 CCSOP K 接口
                    |
CCSOP KingClub 业务实例（一个业务后端，内部按职责分模块）
  商品与批次库存 ── 订单/收银/履约 ── 经营账/会员账/财务账
                    |
        MySQL 8.4：事务、唯一约束、流水、审计、待办事件
                    |
        外部适配器：支付渠道 / 配送 / SUPERVM
                    |
        回调与查单 -> 验证结果 -> 同一个幂等业务入口
```

不新增微服务集群、消息中间件品牌、独立会计服务器或通用工作流引擎。现有 Redis/任务能力用于缓存、过期扫描与外部结果补查；MySQL 才是经营业务事实来源。一个部署单元内使用模块函数与受控 Repository，不让每个模块绕道 HTTP 调自己。

手机是主要经营端，吧台收银机是固定桌台看板/收银/打印终端；不是另一套后台账。收银机操作系统和打印机尚未核实，业务模型先共用，显示适配与打印以独立端口处理，详见 [终端设计](MOBILE_AND_COUNTER.md)。

## 2. 各层负责什么

| 层 | 负责 | 不负责 |
|---|---|---|
| Flutter 页面 | 商品选择、数量、收货/盘点/支出输入、明确结果和重试入口 | 不算权威售价、库存、可退款额或最终支付结果 |
| 用例层 | 报价、开单、付款确认、采购入库、盘点、退款、记账的编排 | 不把一个大存储过程原样搬成一个万能类 |
| MySQL / 受控 Routine | 原子预留/扣减、唯一幂等键、订单状态、资产流水、账务凭证及审计 | 不在持锁事务中等待支付、物流或链节点 HTTP |
| 支付适配器 | 创建支付、查单、关闭、验签、退款和退款查询 | 不直接改商品/会员/库存表；统一交给业务用例 |
| SUPERVM 适配器 | 读取能力、准备已绑定订单的交易、提交用户签名交易、查询回执与权属 | 不自动替用户签名，不让链回执直接更新 MySQL 余额 |
| 通知 / 任务 | 持久任务重试、提示客户端刷新、异常待办 | 不作为支付已完成或库存已扣减的唯一证据 |

App 依赖语义 Repository，Fake/真实 adapter 在装配处切换。按账号、门店、开台/订单隔离草稿；退出或身份变化废弃迟到响应。已有 commerce Fake 可以借鉴测试，但不能把其数据模型当作真实后端契约。

## 3. 五个职责模块足够

1. **商品和库存**：受控供应商/商品、套餐/调酒用量、批次、采购、入库、预留、出库、盘点、易耗品领用及吧台用酒；产品对外查询使用同一库存状态。
2. **订单和收银**：会员/预约/本次开台关联，到店/自提/配送/链上订单、报价、收款、退款、交班、履约、桌台看板与打印任务。
3. **账务**：经营收支、吧台备用金调拨/领用、会员资产、凭证/总账/报表。业务事实共用，不重复生成收入或费用。
4. **经营权限**：老板、员工与按需财务访问，单店默认；订单归属/仓位/数据访问在服务端检查。
5. **外部适配**：支付、配送、自提凭证、VM；每种交易有独立可恢复状态。

这些是代码职责，不是五个独立服务。商品管理和扫码菜单共享 Catalog；收银和扫码共享 Order/Inventory/Accounting 用例，不开发两套库存。

## 4. 关键事务

### 4.1 下单预留

服务端验证门店、桌台/渠道、商品版本、数量与可用资产；按固定顺序锁定所需库存，套餐展开为组成数量；重新确认 quoteRevision。单事务创建订单、库存预留、必要的会员资产占用和支付尝试记录。任一商品不足全部失败，返回需调整商品；不部分扣减后由页面修复。

提交后外部创建支付可能失败或未知，仍有本地订单可查询。同一用户同一幂等键重试返回原结果；相同键不同输入拒绝。

### 4.2 付款成功自动出库（用户已确认）

验签和商户/订单/币种/金额检查在进入业务写入前完成。随后锁定支付尝试、订单和预留，在一次数据库事务内：

- 确认支付结果且唯一消费该支付事件；收款渠道流水不重复记账。
- 将预留转为按批次销售出库，保存成本；扫码商品可售量立即反映结果。
- 确认会员抵扣/奖励（若该商品规则需要），以订单业务键去重。
- 生成收款/库存等账务事实、适用凭证、待交付任务和事务待办事件。

已付款待上菜/待自提/待发货属于“已售待交付”，不会再次占用可售库存。上菜/发货只转移待交付状态，不能再次销售出库。只读 API 随时能恢复结果，不依赖 WebSocket 消息恰好到达。

### 4.3 取消、超时、迟到成功

过期任务先查询/关闭支付尝试，取得明确不可再支付/未支付的结果后释放预留。外部状态未知就维持待确认并进入异常待办，不自动释放后再假定付款失败。

在关闭与成功并发时，以锁和唯一状态迁移保证只有一次处理。若历史/异常支付在库存已释放后仍真实成功，优先重新校验并原子取得库存；不足则进入“已收款待退款/人工处理”，禁止超卖或显示未付款。通过原支付尝试恢复，不创建第二次扣款。

### 4.4 采购与盘点

采购、实收、付款各有身份；“采购并入库且已付”是合并操作界面，不是把三种事实混成一行。入库事务建立批次、增加库存、保存库存金额与应付/已付关联。多次收货只累计实际数量，不能重复入同一收货单。

盘点生成差异调整，锁定确认时相关库存，计入盘点期间销售/入库/退货。数量与金额更正保留来源，不能直接覆盖商品的数量字段。价格变更不回写已售批次成本。

### 4.5 受控档案、易耗品、用酒和备用金

采购强制使用启用 supplierId/productId，后端验证引用和权限；员工不能借采购接口创建任意供应商/商品。收货单保留档案当时名称及版本，后改名称不改变原单。

易耗品默认不上商店，领用/损耗与销售出库使用不同原因和成本模板。后仓转吧台是位置调拨，保留批次，不产生销售收入。开瓶按档案容量转换基本单位，不重复入库/采购。

鸡尾酒用简单配方复用组成扣减：付款按已批准用量扣原料，吧台记录理论量/实际量；已扣部分只确认记录，差异经授权生成调整。不关联销售的试饮/训练/损耗使用独立原因。配方/容量缺失时不开放无法准确核算可售数量的商品，先在档案补齐。

备用金领用同时减少来源账户、增加吧台钱箱，记录领取人及实际操作人；归还反向处理，费用另记。交班绑定钱箱、班次和调拨，不把员工个人会员钱包当钱箱。

## 5. 三层账的最小实现

日常收支与订单产生统一的 businessEventId，关联单据、库存/资产流水和凭证。一次销售可产生多个不同职责的事实，但每个事实只能记一次。

不建设可拖拽的复杂会计规则平台。初期以少量可版本化的业务模板实现：采购收货、采购付款、销售收款、履约与成本结转、经营支出、退款/退货、充值/消费、佣金、盘点调整。特殊业务放待分类清单，由老板/会计补充。

凭证在服务端验证借贷平衡和期间状态；日常员工只选业务分类。总账/报表由已过账分录生成，不能拿 k_bill_detail 的通知内容当总账。用户要求的完整报表能力保留，日常入口不强迫显示它。

## 6. SUPERVM 的位置

本地仓库目前对外名称 NOVOVM，路径仍 SUPERVM。已读证据：

- `README.md` 说明原生转账/AOEM 路径及其验证边界，不保证任意商业交易或完整主网已经验收。
- `docs/NOVOVM_NATIVE_TRANSACTION_AUTHENTICATION_V1.md` 约定签名、chain domain、nonce 和持久化重放处理；公开高层操作需要用户签名，不由服务代签。
- `crates/novovm-node/src/main.rs` 有 nov_buyAsset 和 nov_getReceipt/nov_getTransactionReceipt 分流；`native_block_ledger.rs` 有回执承诺/区块相关结构。
- KINGCLUB 已有传输相关用途不代表商店支付或资产交割已实现。

**建议接法**：CCSOP 负责商店订单、人民币账、实物库存和履约；VM 负责已明确资产的链上执行/权属与回执，CCSOP 只记录可核验的映射和结算状态，不再维护一份可随意修改的“链上余额”。

先通过一个 `ChainCommercePort` 收口，不改 VM 内核。提案操作：capabilities、prepareIntent、submitSignedIntent、getReceipt、getOwnership；具体 RPC 方法和字段必须按实际节点能力验证，本文不预设已全部可用。

订单绑定 network/chainId、assetId/合约、tokenId（若适用）、卖方、买方、收款方、数量、价格单位、费用、到期时间、业务意图摘要。收到任意 txHash 不算成交；需验证与该意图一致、执行成功、达到已确认的最终性策略，且权属/交割结果正确。

正常用户只看到资产名、价格/费用、账户、签名确认和成交进度；高级页可查交易证明。失败、签名拒绝、网络不匹配、费用变化、重试、长时间未确认均有明确状态。网络转发 ACK 与商业最终确认绝不混用。

跨链、跨法币/链资产兑换、第三方卖家担保/托管、自动做市不是从“链上商品”自动推导出的需求。先确定具体交易品类和资产托管方式；无需为了普通到店订单让整套系统依赖 VM 可用性。链节点不可用只影响链上购买。

## 7. 权限和发布隔离

默认老板/店员两类角色，财务高级权限可按人额外授予；用户账号沿用现有真实会话的不透明标识，不重建登录体系，也不固定仅支持 U 前缀。员工成本可见、退款、盘点调整和报表权限独立控制，默认不开给普通会员。

审计 actor 取可信会话，服务器记录确认时间和终端，不接受客户端伪造操作员工。库存、资金、账务变更带业务事件/来源单据及更正引用；系统自动出库标记 system 执行并追溯原下单会员/操作员工。实际领取人或消费者另列业务字段，不冒充操作者。

桌台状态来自预约和本次开台/入座的业务事实；扫码点单以服务器确认的 member→seating→session 关系授权。同桌可代付不等于可查看他人资产，消费归属与 payer 分开。手机/收银机并发操作用资源版本，历史订单不随换桌静默改写。

新服务未来若进入开发，须单独建立后端 worktree，先重新核对其 AGENTS 和 migration 序列；本轮不在聊天后端工作区写入或部署。App 此分支只做 commerce 文档；公共路由、接口执行器、会话等合入点单独记录，完成后在独立集成工作区协调，不能覆盖聊天未提交内容。

## 8. 防止过度设计的取舍

默认单店、后仓/吧台按岗位带位置、自动选批次、先付款、简单经营分类、同一种交付/货币尽量一单、月度导出。保留最少必要的订单、批次、库存流水、支付、凭证身份，不因少人使用而省掉事务、幂等和追溯。

审批流设计暂为普通操作直接完成、异常由老板处理；未来真有明确需要再扩展。物流先支持自提和可追踪的手工发货信息，具体配送服务后定。链上操作独立开关和状态，不迫使每个店员学习区块链参数。

## AA 业务补充（用户最新确认）

参见 [AA 入局、共享套餐与加餐](AA_AND_SHARED_PACKAGE.md)。点单必须提供「直接买单 / 发起 AA」。抖音、美团券自助核销或 App 购买后取得入局权益，按卡座容量和男女配比预定；预定与实际入座分别显示。基础共享套餐在员工确认开局、准备酒水时整桌出库一次，不能逐人核销重复出库。加餐 AA 由发起人设置人数，参与者先付各自份额，人数与款项付齐才成单并整单出库，未成团超时退款。此前“付款立即出库”适用于直接买单；买入局券和单人支付 AA 份额不触发整套出库。

## 平台化补充（用户最新确认）

[平台、多经营主体与多门店](PLATFORM_AND_STORES.md) 为本包归属与隔离规则。平台服务不同老板、不同品牌、多地区多门店；地区用于发现，经营主体用于隔离，门店用于实际经营。此前单店/一套主体模板只可解释为单个核算主体的简单默认，不能解释为全平台共用库存、钱包、收款或总账。手机、订台、AA、收银、打印及统计均须带正确范围。

## 开发范围与语言补充

用户确认开店管理和代运营需要另设后台，暂非优先：本期设计并保留多经营主体/地区/门店基础，先做好会员端、员工手机和吧台经营。后续后台不等于当前就做商家入驻、代运营控制台等页面。全软件必须支持简体中文、英文、繁体中文、泰语，见 [四语言设计](LANGUAGES.md)。

## 会员存酒服务

用户已确认 [存酒/取酒与二维码核销](MEMBER_WINE_STORAGE.md)。联动现有 APP 储物柜与动态码，增加员工手机/收银机存取办理和门店权限。会员保管酒不进入可售库存，取酒不重复记销售或扣销售库存；存取事件、实际操作者、归属及二维码均可追溯。AA 余酒归属、计量、期限、代取/跨店规则列为待确认，不能自动分配给发起人。
