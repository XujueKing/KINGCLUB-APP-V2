# 手机管理、会员桌台与吧台收银机

状态：In Review。用户已确认手机管理为主，并需要吧台收银机界面及小票打印。两端共用同一后台、订单、库存和账务，不能各记一套再手工对账。

## 1. 手机端日常管理

员工用自己的授权身份登录：选供应商/商品采购、确认分批收货、查看库存、每日盘点、登记用品领用、吧台备用金、调酒用量、收银/退款和交班。老板也可在手机管理基础清单、看利润、查操作历史及报表。

默认字段由系统带出：操作人、门店、岗位常用位置、时间、班次；员工主要选择对象和填数量/金额。每笔确认在服务器生成来源单号，操作人不可自由输入；真实领用人/收货人可以作为另外的业务对象选择。

断网只允许草稿。恢复后再验证供应商/商品启用状态、当前价格、库存和权限；页面明确区分“本机待提交”和“服务器已确认”。已确认单据修改保存原值、更正值、原因和真实更正人，不覆盖历史。

## 2. 会员、预约和入座关系

用户已确认会员制，会员坐在哪张桌已有记录。旧结构也有：

- k_table：桌台/包厢、容量、空置/使用/预定/打扫状态。
- k_order：tableId、scheduledTime、operateUserId、isOver 等开台/预约关联。
- k_order_member：orderId、userAccount、memberStatus（待入场/入场/离场）、enterTime、leaveTime。

新设计沿用已有会员身份及预约/入座事实，先核实其现有新服务契约；本轮不创建第二套会员库，也不导入旧会员数据。

关系：`门店 → 桌台 → 本次开台/预约 → 入座会员 → 消费订单 → 支付/交付`。

同一桌不同时间有不同开台；预约未入座、当前入座、离场/清台分别表示。当前坐着人也可能已有未来预约，两者应能同时展示，不能用一个状态覆盖另一个。

到店订单必须确定所属开台和消费归属；付款会员、下单会员、消费会员、收银员工是不同字段。一个会员替同桌付款时，钱从付款方产生，不把所有入座成员都当付款人。具体同桌消费分摊/代付规则待确认，不擅自实现均摊账或开放他人钱包。

扫码时服务器验证会员及桌台/开台关系，不仅凭可复制二维码文本授权。会员当前不在该桌时显示正确桌位或请求员工确认；不能自动把会员迁桌。未入座的配送/自提/链上商店订单不强加桌台。

员工换桌操作追加事件：原桌次、目标桌次、成员、开始/结束时间和操作人；已有订单保留原发生归属，后续消费按新有效关系归属。转移未完成订单需要明确操作并记录，不能简单改所有历史 tableId。

## 3. 收银机主界面

大屏/横屏触控优先，具体技术载体取决于实际机器系统；不现在假定已能运行 Flutter Windows、安卓或某浏览器壳。

建议布局：

```text
顶部：当前员工 / 班次 / 营业日 / 同步状态 / 搜桌号或会员

左侧：全部 | 空闲 | 已入座 | 有预约 | 待处理

中间：桌台卡片网格                         右侧：选中桌详情
  桌号 / 入座人数 / 当前开台时间                  入座会员、服务员工
  消费总额 / 已付款 / 待确认                     本次消费、加单、退款
  下一预约提示 / 待上菜提示                      当前/后续预约
                                                收银、上菜、打印

底部：待处理支付 / 待打印或打印异常 / 交班
```

每桌应展示：

| 类别 | 字段与口径 |
|---|---|
| 桌台 | 桌号、桌型/容量、空闲/使用/待清台等状态 |
| 入座 | 当前会员列表/人数、入座时间、本次开台、服务员工；离场记录可展开 |
| 预订 | 预约时间、预约会员/人数、确认/取消/待到店，未来预约与当前入座并存 |
| 消费 | 本次开台商品消费、已取消/退款、支付成功额、待付款/确认中额；不把预留订单都算到账 |
| 履约 | 待上菜/待取、已交付和异常，点开能定位到订单行 |
| 快捷操作 | 查看明细、为会员加单/收款、交付确认、打印消费单/小票，按权限显示 |

金额口径统一从服务端汇总已确认单据。原价、优惠、实付、已退、退款中分别有明细；多个会员/多次加单不会把同一付款重复加总。屏幕不默认展示身份证、手机号、私人钱包余额等无关资料，会员身份使用必要昵称/会员标识。

手机变更、线上付款和入座更新后，后台通知收银机刷新对应桌台。断线显示最后同步时间及只读状态，重连按版本补全，不能继续用旧画面收款或声称实时。

## 4. 收银机操作人怎么记录

收银机是共享设备，但不能只有一个永远在线、所有员工共用的管理员身份。终端身份（哪台机器/哪家店）与操作员工分开记录，换班要切换实际操作人，离开时能锁屏。

现有 App 有单活动会话约束，不能为了收银机擅自放宽或让员工手机被挤下线。建议后续评审一个独立终端操作授权：员工在自己手机验证后扫码上岗，服务器签发限定终端/门店/动作范围的短期 OperatorGrant；不复制手机完整 session/refresh token。每个写操作记录 terminalId + verified actor + grant/session 来源。实际实现需与身份模块协调，不能绕过被冻结的注册登录流程。

用户操作与自动事件分别留痕：比如会员扫码付款，自动出库记录系统处理、原下单会员、支付证明；如果收银员代开单，另记实际员工。小票补打记录补打员工，不覆盖原收款员工。

## 5. 打印小票

用户已确认小票打印能力；具体票种为待评审建议：

| 票种 | 内容 | 条件 |
|---|---|---|
| 消费清单 | 门店、桌号/开台、订单/时间、商品数量/单价、优惠、合计、已付/待付 | 未结时明确“消费清单/未结”，不能打印成已付款凭证 |
| 收款小票 | 上述必要明细、实际支付组成/金额、收款时间、收银员工、票号 | 仅服务器确认成功的付款；不从页面自报状态生成 |
| 退款小票 | 原票引用、退项、金额、已退/处理中状态、操作人 | 退款成功与申请分开，不把申请当已退 |
| 补打 | 原票/订单和当时快照、补打标识/次数 | 不生成新订单、出库或凭证；留补打操作记录 |

吧台制作单/分单打印如有需要后续明确，不因“小票”二字自动扩展多档口排单系统。

后台生成版本化 ReceiptSnapshot/PrintJob；终端通过 PrinterPort 输出。状态至少 queued/sent/confirmed（设备支持时）/failed/unknown。接口已发送不等于纸已打印；断线/缺纸/状态未知时提示查看打印机，可手动补打并明确标识，避免无条件重试连续打印。

票据不含完整手机号、会员资产余额或支付密钥；打印查询二维码若有，只引用受限订单信息，不成为付款/退款授权。打印故障不能回滚已到账支付和库存出库。

尚需收银机操作系统、屏幕尺寸、打印机型号、连接方式（USB/网络/蓝牙等）、纸宽和驱动/指令支持。没有这些信息先完成版式/端口契约，不下载驱动或在真实收银机/聊天测试手机上试装。

## 6. 本模块验收

- 手机采购/收货后收银机商品和缺货状态一致；不能存在两套库存。
- 一桌两名会员、三次加单、一次退款时，明细与汇总正确，payer 与 consumer 不混淆。
- 当前入座与稍后预约同时可见；换桌和清台不改历史订单。
- 员工甲手机操作、员工乙收银机补打可分别追溯；失权/交班后旧授权不能继续写入。
- 断线时看板明确陈旧；恢复后补齐变化，不重复下单。
- 缺纸/打印超时/补打均不二次收款、扣库存或记收入；未付款不能打印成收款成功。

以上是设计验收项，本轮未做硬件适配或真机测试。

## AA 业务补充（用户最新确认）

参见 [AA 入局、共享套餐与加餐](AA_AND_SHARED_PACKAGE.md)。点单必须提供「直接买单 / 发起 AA」。抖音、美团券自助核销或 App 购买后取得入局权益，按卡座容量和男女配比预定；预定与实际入座分别显示。基础共享套餐在员工确认开局、准备酒水时整桌出库一次，不能逐人核销重复出库。加餐 AA 由发起人设置人数，参与者先付各自份额，人数与款项付齐才成单并整单出库，未成团超时退款。此前“付款立即出库”适用于直接买单；买入局券和单人支付 AA 份额不触发整套出库。
