# AA 入局、共享套餐与加餐

> 最新已确认规则见 [营业规则确认](CONFIRMED_OPERATING_RULES.md)：活动不限报名人数、开局前分配卡座，按各卡座最小/最大人数开台；加餐 AA 有效 30 分钟，未付齐退 APP 余额；AA 门票酒禁存，单点/购买套餐由购买者存酒、仅原店取、保管 3 个月；券按配置选择使用，成本按进货价；收银硬件第二期。本文较早的冲突描述以该确认为准，技术方案仍待评审。

状态：In Review。用户已确认：加餐 AA 逐人先付，人数付齐成单，未成团超时退款；基础套餐由员工确认开局并准备酒水时整桌出库一次。本文件优先补充此前按单人点单编写的规则。

## 1. 两条业务流程

**基础入局**：取得有效入局权益后报名门店活动（如卡颜局）。活动报名无人数上限；开局前自动或人工分配到一个或多个卡座。各卡座按初始化的最小/最大人数和配比校验；达到最小人数可由员工开台，未分配者由人工决定失效和退票。报名、分座和实际入座分别显示。第三方自动核销暂缓。

**加餐**：一个人即可发起，选择自己直接买单，或者拆成若干份并自行找人 AA。直接买单提交预留、付款成功出库；AA 有效 30 分钟，所有份额付齐才成单出库，超时未付齐自动将实付金额退到各付款会员 APP 余额。发起不自动算已付款。代付多份、发起人是否必须参与付款仍需详细定义。

## 2. 第三方核销与入局权益

- 抖音、美团各经独立适配器处理券查询、核销、查结果及适用时的撤销。当前仅为接口设计，尚未验证商家资质、平台接口权限或现有接入能力。
- 手机提交券码不是核销成功；以平台确认的核销结果为准。超时显示处理中并查原请求，不能换新请求重复核销。
- 平台订单/券的唯一标识和核销流水防重；一个已消费的权益不能重复加入多局。
- App 购买以本服务端确认付款生成权益，不凭客户端支付成功页面。
- 核销成功但暂未选局，保留“可选局”权益；尚未分配座位时不丢权益、不假称已分座。有效期、改局及撤销核销规则待定。
- 第三方券面额、平台待结算款、实际到账及平台费用分别记录。自助核销不代表平台款已到账，不将外部成交再计作 App 新收款。
- 不导入旧券或旧会员数据，不在本轮连接平台或试核销真实券。

## 3. 报名、分配和开台

活动报名和卡座开台是独立对象。报名不因某桌满员而拒绝，也不预占某张桌子。分座时原子校验本店卡座的最小/最大人数配置、男女配比、成员是否已分配与版本，自动和人工分配共用约束。

设计状态：报名为待分配 → 已分配 → 已入座，人工失效/退票为分支；卡座本次开台为待分配 → 待开台 → 营业中 → 已结束。达到最小人数允许开台，不等于系统自动开台；最大人数是每桌上限，不是活动报名上限。未分配报名不自动按加餐期限关闭。

## 4. 共享套餐如何扣库存

每次卡座开台对应一份共享套餐履约记录（同一活动分多桌，分别履约），套餐分解成实际酒水商品和数量。**不能每核销一个人的 AA 券就出库一整套。**套餐份数或内容若随人数变化，使用明确的配置规则和版本，不由客户端推断。

建议分两步：
1. 预定形成套餐保障时，每次卡座开台预留一次组成商品；预留时点与未成局释放时限随开局规则确认。
2. 员工确认开局并准备酒水时，按实际批次将整桌套餐出库一次，生成吧台备酒任务。备酒/上桌只确认交付，不再扣库存。

基础套餐可能提前数日预定：不能在单个会员买券时就永久锁一整桌库存。应定义可预定额度和临近开局的实物库存保障；“有席位”和“有套餐库存”都必须满足承诺条件。库存不足时明确待处理/不可预定，不暗中更换酒款。

已确认整桌套餐一次出库；如分次上桌，仅更新交付数量，不能再次扣库存。补发、赠送、破损各有独立原因和授权。

取消时未出库部分释放；已出库但未上桌的酒水，经实物确认可再售才退库。退款和退库存分别记录，不能退款后自动把已喝酒水加回。

## 5. 加餐 AA 的资金和库存

用户已确认：参与者逐人付款，人数与足额付款均满足后，原子确认成团并形成一笔加餐销售订单。创建成功后 30 分钟未凑齐，关闭并将实付金额逐笔退入各付款会员 APP 余额。未付份额不计入已付齐人数，人数齐但款项未齐不能出库。

- 一次参与绑定一个会员和其支付尝试；人数计数按服务端有效参与记录，重复点击/回调不重复计人。
- 最后一名争抢时不得超收人。支付结果迟到与团关闭并发时查明资金状态，进入退款处理，不能重复开团。
- 总金额与分摊方案在发起时由服务端生成；以最小货币单位分摊，尾差公开、总份额严格等于应收。成团过程中不能静默改价或人数。
- 库存按整份加餐锁定，不能只锁某个人付款对应的零碎酒水。预留期限必须覆盖批准的组团/付款窗口；若无法保障，阻止继续收款或走明确失败退款。
- 成团确认、订单生成、库存出库和内部记账应幂等关联同一团；APP 余额退款按原付款流水幂等入账，通过可靠待办重试，不假定多人的渠道付款能在一个数据库事务中回滚。
- 每人收款、退款可单独查询；共享套餐成本按局归集，加餐成本按加餐订单归集，不按参与人数重复确认整套成本。

## 6. 手机、收银台和小票

桌台卡片显示局名/场次、容量与配比、已预定/已入座人数、共享套餐待备/已出/已上桌，以及直接买单和 AA 加餐。
AA 加餐显示“已参加 X/N、已付 X/N、待成团/待付齐/已成单/退款中”，不把待成团金额计为已完成消费。点开可看付款会员与共享消费范围。

小票区分整桌消费清单和单会员付款凭据，标明基础共享套餐、加餐、直接支付/AA、实收与退款；整桌汇总不能再次要求所有会员支付已经付过的钱。
