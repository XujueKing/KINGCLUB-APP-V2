## 关联规则

- 用户最新确认：网址可以更换，兼容协议以 `?` 后的业务参数为准。APP 解析 HTTP(S) 二维码时不绑定旧域名或路径，按参数名称读取 type 与业务标识。例如不同网址的 `?type=9&tableId=T1` 均定位同一桌台；参数顺序不影响新版解析。不访问二维码网址来决定权限。
- 微信与 APP 均需支持桌卡、酒卡、券和门票的业务入口，共享后台业务记录及核销状态。用户确认当前桌卡已能被微信直接打开；未来更换网址时，小程序入口配置的适配与业务参数兼容分别验收，不能仅凭参数相同就声称新网址已通过微信实扫。酒卡、券、门票的新端适配尚待逐项实现。

- 用户看到的 V1 是桌名；tableId 是桌台档案标识。酒吧 ID 对应当前 commerce 的 storeRef，OrderingContext.barId 作为同一值别名，不造两个可冲突的门店身份。
- 城市用稳定 cityId 关联地区目录，cityName 仅展示。归属由后台桌台 → 酒吧 → 城市档案确定，不能从手机 GPS 代替门店城市。
- 旧码只有 tableId 时先按有效历史桌卡映射查询；唯一命中才返回当前酒吧/城市/本次场次。若桌号仅 V1 或多个店有同一旧 tableId，必须用原码 shopId/酒吧上下文进一步确定，不能随机选店。
- 扫码不创建酒吧/城市，也不把二维码声称的 barId/cityId 自动写入档案。这里的“新增关联”是档案和解析结果新增字段；首次没有配置关联时由超级管理员补档，再扫码即可，无需要求每个顾客填写。
- 如码内已有 shopId/barId/cityId，解析服务校验与档案一致，矛盾则拒绝；未知/停用桌、闭店或无当前可用场次返回可解释状态，不伪造一个场次。

## 当前交付边界

已实现兼容解析器和上下文城市字段，并接入相机扫码分支：识别 `type=9` → `/commerce/ordering?tableId=...` → 桌台查询入口 → 现有点单 UI。type 选择业务，tableId 定位桌台，酒吧与城市不是跳转必填参数。当前实际路由尚未配置后端查询器，会明确显示服务尚未接通，不用演示门店冒充扫码结果。单元测试采用合成链接，并非用户图片的实际码值。未建立后端桌台解析接口，未修改新服务器表或建立城市数据。

### 新版好友与群码不是旧 type 规则

核对新服务器 `src/kingclub/profile/personal-qr.ts`：当前个人码签发格式为 `KC:M:` 加随机令牌，有效期 10 分钟；解析还兼容 `kingclub://member/v1/` 加密码，不接受旧 `type=0` 链接。APP 扫码后调用 `K260912000507` 解析个人码，再打开名片供申请好友。群码为 `KC:G:`，已有独立预览分支。因此上表仅说明旧版历史，不是要求把新版好友/群码改回数字 type。此次新增 type=9 点单分支与现有协议共存。

## APP 两处入口统一分发

首页 `HomePage.onOpenScanner` 经 `AppShellPage._openScanner`，以及消息/联系人中的扫一扫均进入 `SafeScannerRoute`（`/scan`）。已配置 API 地址的实际 APP 使用 `MemberScannerPage`；其接入统一的 `ScanRoute.parse`：

- HTTP(S) URL 的 `type=9 + tableId`：原生点单入口，域名和路径可变化。
- `KC:M:` 与兼容的 `kingclub://member/v1/`：原有个人码服务验证及名片流程。
- `KC:G:`：原有群码预览与验证流程。
- 其他码（含尚未接通的旧酒卡/券/门票类型）：明确提示“此二维码无效或对应业务尚未接通”，不请求好友解析服务、不自动核销。

无 API 配置时原有 `SafeScannerPage` 仍是演示流程，不声称可以实际相机扫码。两处入口共享分发，不分别维护协议副本。扫码提示已包含桌卡。

本节点验证：37 项测试通过（统一分发、桌卡解析、桌台入口、首页、AppShell），3 个变更代码/测试文件静态分析通过。保持独立 commerce 分支，未操作聊天测试手机；酒卡、券、门票实际业务适配仍未完成。
