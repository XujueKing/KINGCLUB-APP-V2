# 旧桌卡兼容与酒吧、城市关联

2026-09-18。用户提供 V1 桌卡，要求沿旧小程序识别方法，识别桌号后关联酒吧 ID 和城市。图片可确认用途/显示桌号；本轮未对图片解码，不声称其真实字符串内容。

旧 index.js:831 起 decodeURIComponent 后判类型，case 9 读取 tableId/shopId/tableName。新版 TableOrderingCode 兼容 type=9、tableId，旧 shopId/tableName 可选；新增 barId/cityId 可选，缺少这两个字段的旧卡仍可被解析。不按参数固定顺序截字符串，拒绝重复关键字段/畸形输入。解析器不访问码内网址，也不授予消费或入座权限。

## 关联规则

- 用户看到的 V1 是桌名；tableId 是桌台档案标识。酒吧 ID 对应当前 commerce 的 storeRef，OrderingContext.barId 作为同一值别名，不造两个可冲突的门店身份。
- 城市用稳定 cityId 关联地区目录，cityName 仅展示。归属由后台桌台 → 酒吧 → 城市档案确定，不能从手机 GPS 代替门店城市。
- 旧码只有 tableId 时先按有效历史桌卡映射查询；唯一命中才返回当前酒吧/城市/本次场次。若桌号仅 V1 或多个店有同一旧 tableId，必须用原码 shopId/酒吧上下文进一步确定，不能随机选店。
- 扫码不创建酒吧/城市，也不把二维码声称的 barId/cityId 自动写入档案。这里的“新增关联”是档案和解析结果新增字段；首次没有配置关联时由超级管理员补档，再扫码即可，无需要求每个顾客填写。
- 如码内已有 shopId/barId/cityId，解析服务校验与档案一致，矛盾则拒绝；未知/停用桌、闭店或无当前可用场次返回可解释状态，不伪造一个场次。

## 当前交付边界

已实现兼容解析器和上下文城市字段；单元测试采用合成链接，并非用户图片的实际码值。尚未接进真实相机扫码分支，未建立后端桌台解析接口，未修改新服务器表或建立城市数据。后续应在独立后端工作区核对现有门店/地区来源，再实现解析端口，前端保持会员/群码分支。
