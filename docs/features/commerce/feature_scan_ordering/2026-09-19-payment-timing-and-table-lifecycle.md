## 门店设置与场次快照

- 门店 `paymentTiming`：`prepay`（先付费，默认）或 `postpay`（后付费）。酒吧现有先付费规则保留。
- 员工开台时，把门店付款模式复制到营业场次 `paymentTiming`。营业中改门店设置只影响下一次开台，不改变已成立订单。
- 两种模式都使用开台场次。桌卡 tableId 定位桌台，场次编号区分每轮客人；预约编号不能充当场次编号。

## 扫码入口（待接入预约、入座接口）

| 桌台业务状态 | 扫码后的页面和行为 |
| --- | --- |
| 空台、无本时段预约 | 展示门店和桌号，进入开台确认；默认由员工确认，避免路过扫码直接占台 |
| 本时段预约待到店 | 核对当前会员预约或由员工确认入座后开台；不展示其他会员预约隐私 |
| 已开台、当前会员属于本场次 | 直接进入点单，可复购并查看本场次“已点” |
| 已开台、会员尚未关联本场次 | 提示确认入座/请员工处理；扫到二维码不等于加入该桌或获得赊账资格 |
| 清台中 | 提示员工正在处理，暂停新增订单；不能把新订单挂到旧场次 |
| 停用、暂停营业 | 明确提示不可点单，不回退其他门店或示例数据 |

预约判断以门店营业时区和预约时段为准；未来预约不直接锁死当前空台。活动报名仍不限总人数，先分桌，再根据该桌最小/最大人数及已确认规则开局；每桌基础套餐出库一次。预约冲突处理和自动开台不是本次已经实现的能力。

## 点单与“已点”

- 点单页增加“已点”入口，查看本场次订单与逐项上菜进度。购物车是未提交商品，已点清单是服务端已提交订单，不能混用。
- 支付状态与上菜状态分别记录：待付款/已付款/退款中/已退款，以及待备货/待上/部分已上/已上/已取消。一个订单可有多行、同一行可部分上菜；保留应上数量、已上数量与员工操作记录。
- 先付费：提交预留，付款成功成单并出库，进入待上；AA 仍为 30 分钟全部付齐成单，失败退款到 APP 余额。付款成功不能自动记作已上。
- 后付费：提交时原子检查可售库存，确认订单形成应收并出库，进入待上；结账结清该场次应收。失败不生成可履约订单；取消/退货按是否实际出库和退回处理，不能简单加回库存。
- 加餐 AA 保留原定“全部先付齐才成单”的独立规则，后付费门店选择 AA 时也明确展示这一规则，不产生既记应收又重复支付的同一份金额。
- 普通会员仅可操作自己的付款、优惠券和退款；同桌“已点”展示范围以后端入座关联控制，不通过二维码公开支付人隐私。员工可看整桌。

## 清台

默认员工发起。场次状态 `open → clearing → closed`，清台中禁止新点单；服务端事务锁住场次，和同时发生的点单/支付/退款竞争时只允许合法结果。

关闭前检查未付/未结应收、未成团 AA、退款处理中、未完成上菜/取消，以及待处理库存事项。未完成事项必须结清或明确取消、退款/报损处理后才能关闭，不能把“清台”当作抹账按钮。无法完成时恢复 open 或保留清台中并明确原因。

关闭只清空当前桌台展示和本地草稿；历史订单、支付、出库、上菜、操作人及场次留存。下一轮生成新场次，已点列表从零开始。延迟支付回调仍查原订单/原场次，绝不能计入下一桌。
