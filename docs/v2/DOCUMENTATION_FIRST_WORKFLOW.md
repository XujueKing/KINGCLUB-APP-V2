# 文档先行开发流程

## 1. 强制规则

每一个功能和每一个页面都必须拥有独立文档目录。功能文档设计未完成前，不得开始该功能的 Flutter 开发；页面文档未完成前，不得创建该页面实现。

标准顺序：

```text
提出需求
  -> 建立功能目录
  -> 完成功能规格并评审
  -> 建立页面目录
  -> 完成页面/交互/API/验收设计并评审
  -> 创建 Flutter 实现目录
  -> 编码与测试
  -> 验收与归档
```

## 2. 功能开发准入 Definition of Ready

以下内容全部完成，功能才可进入开发：

- 目标、用户价值、范围和不做事项明确。
- 用户角色、入口、前置条件和主流程明确。
- 状态机与异常流程明确。
- 页面清单和页面间导航明确。
- 数据模型、API 契约、权限和错误码明确，或有批准的 Mock 契约。
- 埋点、日志、隐私、安全和合规要求明确。
- 验收标准和测试场景可执行。
- 依赖、风险、灰度和回滚方式明确。
- 文档状态标记为 `Approved for Development`。

缺少任何一项时，状态保持 `Draft` 或 `In Review`。

## 3. 页面开发准入

页面目录至少应包含：

- 页面目标和用户任务
- 入口、出口、返回行为和路由参数
- 信息架构与组件清单
- 加载、成功、空、错误、无权限、离线和会话过期状态
- 交互规则、校验、弹窗和防重复提交
- API 字段映射或 Mock 数据
- 设计稿链接/版本；无设计稿时提供明确线框说明
- 埋点与可访问性要求
- Widget/集成验收用例

## 4. 文档状态

| 状态 | 含义 | 是否允许编码 |
|---|---|---|
| Draft | 草稿，边界可能变化 | 否 |
| In Review | 正在产品/设计/技术评审 | 否 |
| Approved for Development | 需求与契约达到开发准入 | 是 |
| Implemented | 已实现并通过开发测试 | 是 |
| Accepted | 已完成业务验收 | 是 |
| Deprecated | 已废弃，仅保留历史 | 否 |

## 5. 变更控制

- 开发后需求变化，先更新文档和验收标准，再修改代码。
- 影响多个功能的决定记录为 ADR，并链接到所有受影响目录。
- API 字段变化必须先更新 OpenAPI/Mock 契约，再生成或修改客户端模型。
- 紧急修复可以缩短评审，但不能跳过问题、方案、影响范围和验证记录。

## 6. 完成标准 Definition of Done

- 实现与已批准文档一致。
- 核心规则、Widget 和关键集成测试通过。
- 加载、空态、错误、弱网和权限状态已验证。
- 日志无敏感信息，埋点和监控可用。
- Android/iOS 目标真机完成冒烟。
- 文档补充实现差异、已知限制和发布说明。
- 产品或指定验收人将状态更新为 `Accepted`。
