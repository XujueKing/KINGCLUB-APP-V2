# 功能分块总览

## 1. 分块原则

- 以用户目标和业务所有权划分功能，不按旧版文件位置机械复制。
- 一个功能只负责一个清晰业务能力；一个页面只承担一个主要用户任务。
- 功能目录拥有自己的模型、状态、用例、页面和测试。
- 支付、聊天、订单、身份等高风险域不得通过公共工具类绕过边界。

## 2. 平台与基础能力

| 业务域 | 功能块 | 主要输出 | 优先级 |
|---|---|---|---|
| foundation | 应用启动与环境 | 配置、初始化、错误兜底 | P0 |
| foundation | 路由与导航 | 守卫、深链、导航框架 | P0 |
| foundation | 设计系统 | Token、基础组件、主题 | P0 |
| foundation | 网络与错误 | API 客户端、统一错误、重试 | P0 |
| foundation | 会话与安全存储 | Token、刷新、退出、设备会话 | P0 |
| foundation | 日志与可观测性 | 崩溃、性能、埋点、requestId | P0 |
| foundation | 权限与原生能力 | 相机、相册、通知、定位 | P1 |

## 3. 用户业务域

### identity：登录与身份

功能：启动检查、手机号登录、验证码、注册、协议确认、实名认证、资料初始化、账号注销。

候选页面：启动页、登录页、验证码页、注册/协议页、实名认证页、资料完善页、账号安全页、注销确认页。

### home：主页与发现

功能：首页聚合、运营入口、附近/同城、搜索、推荐内容。

候选页面：首页、同城列表页、全局搜索页、搜索结果页、运营专题页。

### social：用户关系

功能：用户资料、关注、好友、黑名单、可见性、举报。

候选页面：用户主页、好友列表、关注/粉丝列表、黑名单页、举报页、隐私可见性页。

### messaging：聊天与通知

功能：会话列表、单聊、群聊、消息发送、媒体消息、已读状态、转发、引用、推送跳转。

候选页面：会话列表页、单聊页、群聊页、聊天详情页、群成员页、媒体预览页、转发选择页。

### content：短视频与作品

功能：内容流、作品详情、发布、草稿、点赞、收藏、评论、分享。

候选页面：视频流页、作品详情页、作品发布页、发布设置页、草稿箱、评论页、收藏页。

### club：门店与到店服务

功能：门店、座位/桌台、预约、组局、门票、入场、存酒。

候选页面：门店列表、门店详情、座位选择、预约创建、预约详情、组局详情、门票列表、入场码、存酒列表/详情。

### commerce：商品、订单与支付

功能：商品浏览、购物车、扫码点单、订单创建、订单查询、支付、退款、售后。

候选页面：商品列表、商品详情、购物车、确认订单、收银台、支付结果、订单列表、订单详情、退款申请/详情。

### membership_wallet：会员与资产

功能：会员资格、金币、余额、明细、充值、提现、礼物、红包。

候选页面：会员中心、金币页、余额页、资产明细、充值页、提现页、礼物面板、红包创建/领取页。

### profile_settings：个人中心与设置

功能：个人资料、头像、兴趣、绑定、安全、通知设置、隐私、帮助与反馈。

候选页面：个人中心、编辑资料、兴趣设置、绑定管理、设置页、通知设置、隐私设置、帮助中心、反馈页。

### operations：代理与经营管理

功能：代理、客户、门店经营和低频管理能力。

候选页面：代理中心、客户列表/详情、经营数据、门店管理。该域默认不进入首版 MVP。

## 4. MVP 建议边界

第一版优先形成以下纵向闭环：

1. 启动、登录、会话恢复与退出。
2. 首页核心信息与用户个人中心。
3. 好友列表、会话列表和稳定单聊。
4. 门店/商品只读信息、订单列表与详情。
5. 订单创建、服务端计价、支付与结果确认。
6. 推送跳转、基础日志和崩溃监控。

暂缓：全量群管理、复杂内容发布、代理后台、所有历史活动入口、低频经营页面。

- **当前建议**：先完成“登录 → 首页 → 订单详情”只读闭环，再接聊天和交易写路径。
- **待用户决策**：首发版本是否必须包含短视频发布、群聊、红包、提现、代理和存酒。

## 5. 功能依赖顺序

```text
foundation
  -> identity/session
      -> home/profile
      -> social -> messaging
      -> club/catalog -> commerce/order -> payment
      -> content/publish
      -> membership_wallet
```

任何下游功能开始前，必须确认其上游契约已稳定或已有明确 Mock 契约。
