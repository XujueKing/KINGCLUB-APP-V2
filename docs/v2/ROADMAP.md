# KINGCLUB APP V2 Roadmap

Roadmap 按可验证结果划分，不以页面数量或代码量作为完成标准。具体排期必须在团队规模、API 现状和 MVP 范围确认后制定。

## Stage 0：本期范围与资产基线

当前状态：`Completed — M0 Scope Frozen`。用户已于 2026-08-24 确认 48 页消费者首发基线及不做清单。

目标：冻结本期 App 到底包含哪些功能和页面，以及明确不做什么。

交付物：

- 本期功能/页面总清单与唯一编号
- 明确的“不做清单”和后续版本候选清单
- 旧页面、接口、数据表、角色和权限映射
- 启动、登录、聊天、订单、支付等用户旅程与状态机
- 技术选型 ADR、风险、外部服务和发布输入清单

退出门槛：每个本期页面都有归属功能、用户任务、入口/出口和计划文档目录；清单外功能不得混入 UI 开发。

## Stage 1：全部功能与页面文档

目标：在创建 Flutter 页面前完成本期 App 的全部设计和契约评审。

交付物：

- foundation、design system 和所有业务功能独立文档
- 每个页面的 UI 结构、状态、交互、导航、Mock 数据和验收用例
- 全局设计 Token、基础组件、多尺寸、亮暗主题和可访问性规则
- API/WebSocket/SDK 只作为契约输入，不进行真实客户端接入
- 全 App 用户流程图、异常流程和页面跳转图

退出门槛：本期清单内所有功能和页面均达到 `Approved for Development`；未完成一项也不得开始 Flutter UI。

当前服务端基础与登录页面资料见 [BACKEND_FOUNDATION_PHASE.md](BACKEND_FOUNDATION_PHASE.md)。本期已有 46/48 页文档批准，设置与安全已归档；私人储物柜最后两页评审包已形成；Flutter 工程尚未创建。

## Stage 2：全 App UI 与 Mock 流程

目标：只使用 Mock/Fake 数据完成本期全部页面和完整用户体验，不连接真实服务。

交付物：

- Flutter 工程、app/core/shared/features 目录和设计系统
- 本期全部页面 UI、加载/成功/空/错误/离线/无权限/会话失效状态
- Fake Repository、Fake Session、Fake WebSocket、Fake 支付/推送事件
- 可重复演示的启动、登录、首页、社交、聊天、内容、门店、订单、支付、会员和设置流程（以最终本期清单为准）
- Widget、golden、可访问性和 Mock flow 自动化测试

严格禁止：访问真实 `/supper-interface`、真实 WebSocket、发送真实短信、拉起真实支付、注册真实推送或读取真实用户业务数据。

退出门槛：本期所有页面达到 `UI Mock Implemented`，整 App 主流程、异常流程、返回路径和多尺寸体验可完整模拟。

## Stage 3：整 App UI 流程验收

目标：在任何真实接入前，由用户/产品对完整 UI 和交互流程做统一确认。

验收内容：

- 页面完整性和功能入口无遗漏
- 视觉层级、文案、组件、动效、返回和弹窗一致
- 加载、错误、空态、离线、权限、会话失效等状态符合预期
- Mock 数据不会掩盖字段、状态机或权限缺口
- 明确移出本期的功能已经从导航和 UI 中删除

退出门槛：项目级状态达到 `UI Flow Approved`。未达到时不得开始任何真实接口或 SDK 接入。

## Stage 4：真实基础能力与身份接入

目标：在不改变已验收 UI 语义的前提下，用真实 adapter 替换 Fake。

建议顺序：环境与诊断 → 超级接口网络层 → 安全存储 → 登录/刷新/K104 → WebSocket 会话。

退出门槛：真实测试账号完成启动、登录、会话恢复、顶号、退出和错误路径；Mock 仍可独立运行。

## Stage 5：真实业务能力接入

按已经验收的 UI 流程逐域替换 Fake：

1. 首页与个人资料只读
2. 社交关系与消息
3. 内容与媒体
4. 门店、预约和商品
5. 订单、支付与退款
6. 会员、金币、余额和其他本期能力

每个域必须通过契约、权限、弱网、幂等、数据对账和回滚测试；页面不得直接依赖真实 adapter。

退出门槛：本期全部功能达到 `Integrated/Implemented`，真实结果与已批准 UI/Mock 契约一致。

## Stage 6：稳定、灰度与迁移

目标：达到可发布和可运营标准。

交付物：Android/iOS 真机兼容矩阵，性能/崩溃/弱网/安全/可访问性报告，数据与金额对账，灰度/回滚/客服/监控方案，以及旧多端容器迁移条件。

退出门槛：核心业务指标稳定，新旧结果持续一致，具备明确回滚路径。

## 建议里程碑

| 里程碑 | 可验证结果 |
|---|---|
| M0 范围冻结 | 本期功能/页面总清单和不做清单确认 |
| M1 文档冻结 | 本期全部功能、页面、设计系统和 Mock 契约批准 |
| M2 UI Mock 完整 | 全部页面 UI 与整 App Mock 流程可演示 |
| M3 UI Flow Approved | 用户/产品完成整 App UI 流程验收，允许真实接入 |
| M4 真实集成完成 | 超级接口、WebSocket 和本期业务 adapter 全部接通 |
| M5 首发候选 | 真机、数据、运营、灰度和回滚验收通过 |

## Roadmap 调整规则

- API、设计或产品范围未确认时只能继续补文档，不得用临时 UI 或真实返回替代决策。
- 本期全部文档批准前不开始 UI；全部 UI Mock 流程批准前不连接真实服务。
- 高风险功能不得为了赶页面进度跳过状态机、异常流程和验收用例。
- 每个 Stage 结束后重新评估范围、质量、服务端准备度和用户反馈。
- 新功能必须进入 Roadmap 和功能地图，禁止在开发中临时塞入已有模块。
