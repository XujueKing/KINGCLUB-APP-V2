# KINGCLUB APP V2 Roadmap

Roadmap 按可验证结果划分，不以页面数量或代码量作为完成标准。具体排期必须在团队规模、API 现状和 MVP 范围确认后制定。

## Stage 0：产品与资产基线

目标：在写 Flutter 业务代码前，明确要做什么、依赖什么以及如何验收。

交付物：

- Flutter MVP 功能清单与明确的“不做清单”
- 旧页面、接口、数据表、角色和权限映射
- 用户旅程与核心状态机：登录、聊天、订单、支付
- 技术选型 ADR 与风险清单
- 功能/页面文档模板和评审机制

退出门槛：首个纵向切片的功能规格、页面规格、API 契约和验收用例全部通过评审。

当前 Stage 0 的服务端第一批基础工作见 [BACKEND_FOUNDATION_PHASE.md](BACKEND_FOUNDATION_PHASE.md)，本地设计与异常矩阵门禁已经通过。启动鉴权页与手机号登录页已批准开发，验证码页等待批准完整评审稿，协议确认页尚待正式评审；四页批准后才进入 Stage 1 工程骨架和对应页面开发。

## Stage 1：工程与设计系统底座

目标：建立可持续扩展的 Flutter 工程骨架。

交付物：

- app、core、shared、features 基础目录
- 环境配置、路由、网络、错误、日志、安全存储
- 设计 Token 与基础组件
- 单元测试、Widget 测试、静态检查和 CI
- Mock API 与开发环境切换

退出门槛：空壳 App 在 Android/iOS 真机启动，基础质量检查可重复执行。

## Stage 2：首个只读纵向切片

目标：验证架构、契约、设计系统和发布链路。

建议范围：启动检查、登录、会话恢复、首页骨架、个人中心、订单列表/详情只读。

退出门槛：真实测试账号可完成主流程；错误、空态、加载、弱网和会话过期均有明确表现。

## Stage 3：社交与消息闭环

目标：提供稳定的好友和单聊能力。

建议范围：好友列表、会话列表、单聊、文本/图片消息、已读、重连、推送跳转。

退出门槛：单连接/单心跳可验证；重复消息、乱序、断网恢复和推送冷启动有测试证据。

## Stage 4：门店、订单与支付闭环

目标：完成 KingClub 核心交易链路。

建议范围：门店/商品、购物车或预约、确认订单、服务端计价、支付、订单状态、退款基础流程。

退出门槛：金额完全由服务端确认；支付回调、重复提交、取消、超时和对账测试通过。

## Stage 5：内容与会员能力

目标：补齐高频增长和留存功能。

建议范围：短视频流、作品详情、基础发布、点赞收藏、会员中心、金币和余额只读。

退出门槛：媒体上传可恢复；内容审核、隐私、失败重试和资产数据来源明确。

## Stage 6：扩展业务

按业务价值逐项选择：群聊、红包/礼物、提现、门票/入场、存酒、代理和客户管理、复杂发布工具。

每项能力独立立项、独立目录、独立评审，不以“旧版已有”为自动迁移理由。

## Stage 7：稳定、灰度与迁移

目标：达到可发布和可运营标准。

交付物：

- Android/iOS 真机兼容矩阵
- 性能、崩溃、弱网、安全与可访问性报告
- 数据和业务对账
- 灰度、回滚、客服和监控方案
- 旧多端容器迁移与下线条件

退出门槛：核心业务指标稳定，新旧结果持续一致，具备明确回滚路径。

## 建议里程碑

| 里程碑 | 可验证结果 |
|---|---|
| M0 规划冻结 | MVP、架构决策、首批功能文档通过 |
| M1 工程可运行 | 双端启动、CI、设计系统和 Mock 通路可用 |
| M2 内部 Alpha | 登录、首页、个人中心、订单只读可用 |
| M3 业务 Beta | 单聊与订单支付闭环可灰度 |
| M4 首发候选 | MVP 完整、真机与运营验收通过 |
| M5 扩展迁移 | 内容、会员和低频业务逐项上线 |

## Roadmap 调整规则

- API、设计或产品范围未确认时，允许使用 Mock 做 UI 验证，但不得宣称功能完成。
- 高风险功能不得为了赶页面进度跳过状态机、异常流程和验收用例。
- 每个 Stage 结束后重新评估范围、质量、服务端准备度和用户反馈。
- 新功能必须进入 Roadmap 和功能地图，禁止在开发中临时塞入已有模块。
